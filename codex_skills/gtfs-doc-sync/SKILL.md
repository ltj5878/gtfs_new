# GTFS Doc Sync

这个 skill 对应你现在很明显的一种习惯：功能推进到一个阶段后，会回头把文档改成“当前代码真实状态”。

## 文档基调

- 描述当前分支已经落地的内容，不写愿景口吻。
- 文档要和代码一致，不拿旧规划充数。
- 优先使用简洁中文总结，必要时用表格压缩信息。

## 重点同步文件

- 根目录 [README.md](README.md)
- [backend/README.md](backend/README.md)
- [frontend/README.md](frontend/README.md)

## 什么时候要动文档

- 新增或下线一块主要业务能力。
- 地区支持状态变化。
- 启动、初始化、导入、测试命令变化。
- 页面路由或主要 API 分组变化。
- 用户体系、管理能力、通知、审计等“完成情况”发生变化。

## 同步方法

1. 先确认功能是真正落地，不拿 TODO 或预留代码写成已完成。
2. 根 README 负责全局完成情况、项目结构、启动与初始化。
3. backend/README 负责后端模块、schema、脚本和 API 范围。
4. frontend/README 负责页面、路由、状态、交互约束。
5. 三份文档里的端口、路径、地区支持和命令要彼此一致。

## 这个仓库里的特殊点

- 文档里要明确 `sf`、`sydney` 是当前主用地区。
- `nyc` 如果仍然只是预留，就不要写成可直接使用。
- 项目默认通过 `start.sh` 起整套服务，后端约定端口是 `5001`。
- 测试方式以脚本为主，不要凭空补成正式测试体系。

## 写法偏好

- 多用“已完成 / 已落地 / 当前支持”这类表述。
- 如果一项能力有前后端不同状态，要明确区分，不要一句话糊过去。
- 当架构没有变时，不要为了凑完整性重写整份 README。
