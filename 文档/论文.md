# 基于GTFS的公交智能分析平台设计与实现

## 摘要

随着城市公交网络规模持续扩大、出行需求日益多样化以及开放交通数据逐步普及，如何将分散的静态时刻表数据、实时车辆数据与面向乘客和管理者的业务功能有效整合，已经成为智慧交通信息系统建设中的关键问题。传统公交信息系统通常存在静态数据更新周期长、实时感知能力弱、分析维度单一、用户交互闭环不足等问题，难以同时满足线路查询、运行监测、准点率分析、换乘辅助、运维管理和个性化服务等综合需求。General Transit Feed Specification（GTFS）及其扩展标准 GTFS-Realtime 为公共交通数据共享和系统互联提供了统一的数据表达方式，为构建跨区域、可扩展、可复用的公交信息平台提供了现实基础。

本文结合“GTFS 公交准点率分析系统”项目，设计并实现了一个基于 GTFS 与 GTFS-Realtime 的公交智能分析平台。系统采用前后端分离架构，后端基于 Flask 构建 RESTful 服务，使用 PostgreSQL 作为核心数据存储，并通过多地区隔离策略支持旧金山湾区、纽约地铁与悉尼三类数据源；前端基于 Vue 3、Pinia、Vue Router 与 Element Plus 构建单页应用，融合 ECharts 与 Leaflet 完成图表分析和地图可视化。围绕公交场景中的关键业务需求，系统实现了 GTFS 静态数据导入、线路与站点查询、实时车辆监控、准点率统计、历史回放、换乘规划、站点可达性分析、用户认证、收藏订阅、通知告警、审计日志、数据质量看板、线路健康度评分、碳排放统计、客流预测和数据导出等功能模块。

在关键实现方面，本文针对公交数据处理与业务响应时效需求，提出并落地了按 `region` 进行多地区数据隔离的数据库组织方式，设计了按表依赖顺序执行的 GTFS 导入机制；围绕实时公交运行分析，构建了面向秒级延误数据的准点率计算与聚合模型，形成线路、站点、小时和系统级多粒度指标；在换乘规划与可达性分析中，采用基于站点前沿扩展与代表班次裁剪的轻量化路径搜索策略，在保证结果可解释性的同时控制查询复杂度。系统还通过日志记录、配置加载、角色权限、自动建表和脚本化测试等机制提升了工程可维护性和可运维性。

本文的实现结果表明，该平台能够较完整地覆盖公交信息服务从数据接入、分析处理到业务展示的主要链路，具备较好的模块化程度、扩展能力和实用价值。系统既可以作为 GTFS 数据教学与实验平台，也可以为后续面向真实城市公交运营场景的功能深化、算法优化和工程部署提供基础。

**关键词**：GTFS；GTFS-Realtime；公交信息系统；准点率分析；Flask；Vue 3

## Abstract

With the continuous expansion of urban bus networks, the diversification of travel demands, and the increasing availability of open transit data, it has become essential to integrate static timetable data, realtime vehicle data, and user-oriented service functions into a unified software platform. Traditional bus information systems are often limited by weak realtime perception, slow data updates, insufficient analytical depth, and incomplete interaction loops between passengers and administrators. The emergence of the General Transit Feed Specification (GTFS) and GTFS-Realtime provides a standardized data foundation for building interoperable, scalable, and reusable transit applications.

This thesis presents the design and implementation of an intelligent bus analysis platform based on GTFS and GTFS-Realtime. The platform is derived from the project implemented in this repository and adopts a front-end/back-end separated architecture. The back end is built with Flask and PostgreSQL, while the front end uses Vue 3, Pinia, Vue Router, and Element Plus. ECharts and Leaflet are introduced for statistical visualization and map-based interaction. The system supports multiple regions through a region-isolated data model and currently covers the San Francisco Bay Area, New York City subway, and Sydney. On top of the shared transit data foundation, the platform implements GTFS static feed import, route and stop query, realtime vehicle monitoring, punctuality analysis, historical playback, transfer planning, stop reachability analysis, authentication, favorites, subscriptions, notifications, audit logging, data quality inspection, route health scoring, carbon-emission statistics, flow prediction, and multi-format data export.

Several practical engineering mechanisms are emphasized in this work. A region-based schema organization strategy is used to support multi-source transit data management; a dependency-aware GTFS import workflow is adopted to guarantee referential consistency; a multi-granularity punctuality model is designed to aggregate route-level, stop-level, hourly, and system-level indicators from realtime delay records; and lightweight search strategies are used in transfer planning and reachability analysis to balance efficiency and interpretability. In addition, configuration management, automatic schema bootstrap, role-based access control, audit tracing, and script-based verification are incorporated to improve maintainability and operational robustness.

The implementation demonstrates that the proposed platform can effectively connect data ingestion, business analysis, and visual presentation into an integrated transit information system. It offers practical value for teaching, experimentation, and future expansion toward more realistic and large-scale smart transit applications.

**Key Words**: GTFS, GTFS-Realtime, bus information system, punctuality analysis, Flask, Vue 3

## 第1章 绪论

### 1.1 课题背景

城市公共交通系统是现代城市运行的重要基础设施，其服务质量直接影响居民日常通勤效率、城市道路拥堵水平以及绿色低碳发展效果。随着城市规模扩大和公交网络复杂度提高，公交线路、站点、班次、票价、实时位置、客流波动和运行延误等数据不断增长，传统依赖人工汇总和离线发布的信息服务模式已经难以支撑高频更新和精细化管理需求。对于乘客而言，需要的不再仅仅是“这条线经过哪些站”，而是“车辆是否准点”“当前该如何换乘”“某个站点在限定时间内可以到达哪些区域”“哪条线路当前体验更好”等更具决策价值的信息。对于管理者而言，除了完成基础数据发布，还需要掌握接口健康、数据质量、运行风险、异常告警和线路综合表现等指标，以支撑日常运维和服务优化。

近年来，开放交通数据的发展为公交信息系统升级提供了新的技术条件。GTFS 通过统一的文本文件格式描述机构、线路、站点、班次、时刻表、票价等静态信息，GTFS-Realtime 则补充了车辆位置、班次更新和服务告警等动态信息[1-3]。借助这一标准体系，不同城市和不同运营机构的数据可以在较低耦合度下接入统一平台，从而使公交信息系统从单一地区、单一展示功能，演进为多数据源、多角色、多功能的综合分析平台。

本项目正是在这一背景下展开。仓库中的系统已经不再停留于基础线路查询，而是形成了一个覆盖静态导入、实时采集、准点率分析、出行辅助、用户服务与运维管理的完整前后端应用。项目采用 Flask、Vue 3 和 PostgreSQL 组成的典型 Web 技术栈，结合 GTFS/GTFS-Realtime 数据模型，在工程上具备较强的代表性与可扩展性。因此，以该项目为基础撰写毕业论文，不仅能够反映软件工程完整开发过程，也能够体现智慧交通场景下数据建模、算法设计、系统实现与工程验证的综合能力。

### 1.2 课题研究意义

#### 1.2.1 理论意义

第一，本文围绕 GTFS 标准展开系统设计与实现，有助于将交通信息标准、Web 软件架构、数据库建模和业务分析方法结合起来，形成一套适用于公共交通软件系统课程设计、毕业设计和工程训练的综合案例。公交系统具有多表关联强、时间维度复杂、地理信息密集、实时与离线数据并存等特点，适合作为复杂信息系统建模的研究对象。

第二，本文以“准点率分析”为主线，同时引入换乘规划、可达性分析、线路健康度评分、客流预测与绿色出行评估等模块，体现了从数据采集到多维指标构造的研究路径。这种路径不局限于界面展示，而是强调由原始数据到业务洞察的加工过程，对于理解交通数据治理、指标体系设计和服务评价具有一定方法论价值。

第三，项目在实现层面采用按地区隔离的数据组织方式，将多个城市的数据源纳入统一结构下管理。这种设计为研究多租户交通数据系统、跨地区业务复用和标准化接口封装提供了可操作的样本。

#### 1.2.2 实际意义

从乘客角度看，平台将线路、站点、班次、实时车辆、准点率、换乘方案、可达性范围、推荐线路和个人收藏统一到一个系统中，减少了乘客在多个应用或多个页面间来回切换的成本，提升了出行信息的获取效率。

从管理者角度看，平台提供了数据库容量监控、第三方接口健康统计、数据时效性、审计日志、异常告警、公告发布和用户管理等运维功能，能够在一定程度上支撑公交信息平台的日常运营管理。与仅面向公众展示的单功能系统相比，这种设计更符合实际部署场景对后台治理能力的要求。

从工程实现角度看，系统将静态数据导入、动态数据采集、业务分析和前端可视化有机结合，既覆盖了软件开发的主干流程，也保留了后续扩展空间，例如更复杂的路由搜索、预测模型升级、消息推送优化和生产级身份认证等。因此，该平台具有较好的教学价值、实验价值和项目延展价值。

### 1.3 国内外研究现状

#### 1.3.1 国外相关研究进展

在国际范围内，GTFS 已成为公共交通开放数据的事实标准之一[1-3]。许多城市交通机构通过公开 GTFS 静态数据和 GTFS-Realtime 动态数据，为第三方出行应用、学术研究和公共服务系统提供数据基础。基于这一标准，大量研究围绕时刻表建模、公交可达性评价、实时路径规划、换乘优化和服务可靠性分析展开。

在交通规划与运营研究方面，Ceder 对公共交通规划、调度和运行优化进行了系统总结，强调了时刻表组织、服务可靠性和运营效率之间的关系[10]。这为公交信息平台中的指标设计和运行分析提供了理论基础。在路径规划算法方面，Delling、Pajor 和 Werneck 提出的 RAPTOR 方法针对公共交通网络中的多目标路径搜索问题，展示了基于轮次和线路访问策略的高效性[11]。该成果说明，面向公交场景的搜索算法不能简单套用普通道路最短路模型，而应结合时刻表和换乘特性设计特化算法。

此外，随着实时交通数据的普及，国外许多研究和工业系统开始将车辆位置、班次更新和告警信息用于可靠性评估与出行辅助。相比早期只展示静态路线的系统，现代交通平台更强调实时性、交互性和多角色协同，即一方面向乘客提供透明、即时的信息，另一方面向管理者提供更细粒度的运行洞察。本文实现的系统总体上延续了这一发展趋势，但在具体工程上采用了更轻量、教学友好的技术路线。

#### 1.3.2 国内相关研究进展

国内在智慧交通和城市计算方向上也高度重视公交数据分析。随着各地公交卡数据、GPS 数据、视频数据和互联网出行服务数据逐步积累，围绕公交准点率评价、客流预测、线路优化和站点服务水平分析的研究不断增多。与国外开放标准生态相比，国内公交信息系统建设往往更加强调本地化应用落地和与业务流程的贴合，例如面向管理部门的可视化看板、面向乘客的实时查询服务以及面向调度的异常监测模块。

然而，从工程实践看，许多系统仍然存在两个典型不足。其一是静态查询与动态监控割裂，线路、站点、时刻表等基础功能和车辆位置、延误、告警等实时功能分属不同系统，用户体验和数据链路不连续。其二是平台虽然具备一定展示功能，但缺乏以标准化数据模型为核心的可扩展能力，当需要增加新的分析模块时，往往需要进行较大规模重构。本文依托 GTFS 标准与多模块统一架构构建平台，正是希望在一定程度上缓解上述问题。

#### 1.3.3 现有研究存在的问题

综合国内外现状，可以将已有研究和系统存在的问题概括为以下几个方面。

第一，数据整合不足。静态数据、实时数据、用户行为数据和后台运维数据经常分散在不同模块，难以形成统一的数据闭环。

第二，分析链路不完整。一些平台只实现了可视化展示，缺乏面向业务决策的指标体系；另一些平台具备后台分析能力，却缺少面向用户的交互呈现。

第三，扩展性不强。在新增地区、扩展业务模块或接入新数据源时，如果系统底层数据模型设计不统一，就会导致开发成本显著上升。

第四，系统工程性不足。很多课程项目或实验性系统忽视了配置管理、权限控制、日志审计、数据导出、测试脚本和部署脚本等工程要素，导致系统难以持续演进。

本文所实现的平台，正是针对上述问题进行设计：一方面依托 GTFS 与 GTFS-Realtime 建立统一的数据基础，另一方面通过前后端分离、模块化接口和多层数据库 schema 扩展方式，将公交数据服务、运行分析、用户功能和管理功能纳入同一工程体系。

### 1.4 研究内容

结合项目实际实现，本文主要完成以下研究与设计工作。

1. 对 GTFS 静态数据与 GTFS-Realtime 动态数据进行梳理，分析公交信息平台所需的核心数据对象、数据依赖关系和业务处理流程。
2. 设计并实现基于 Flask 与 PostgreSQL 的后端服务，形成基础查询、实时监控、准点率分析、分析工具、用户服务与管理运维等接口体系。
3. 设计并实现基于 Vue 3 的前端单页应用，完成线路、站点、地图、准点率、历史回放、管理后台等 31 个页面级路由的交互组织。
4. 构建支持多地区的数据库模式，以 `region` 字段为基础实现旧金山湾区（sf）、纽约地铁（nyc）和悉尼（sydney）等地区数据的隔离存储与统一查询。
5. 基于实时延误记录设计准点率统计模型，形成线路、站点、小时粒度和系统层级的运行评价指标。
6. 实现换乘规划与站点可达性分析模块，并在算法层面采用轻量化的站点前沿扩展策略以适应课程项目和中等规模数据集。
7. 实现收藏、订阅、通知、审计、数据质量、异常告警、线路健康度、碳排放和客流预测等扩展功能，提升平台完整性。
8. 结合脚本化测试与模块验证对系统进行分析，总结当前系统的优点、不足及后续优化方向。

### 1.5 研究方法与技术路线

本文采用“标准分析 + 需求分析 + 架构设计 + 模块实现 + 脚本验证”的研究路径。首先以 GTFS 和 GTFS-Realtime 为基础，对公交静态与动态数据结构进行抽象；然后以项目功能为蓝本提炼用户需求、管理需求和数据处理需求；在此基础上设计前后端分离的总体架构与数据库模式；随后围绕核心模块逐步实现，并通过本地启动脚本、接口脚本和计算脚本进行验证；最后总结系统实现效果与后续改进方向。

技术路线可概括为：

1. 标准化数据接入：以 GTFS ZIP 或目录文件作为静态输入，以不同地区的 GTFS-Realtime 接口作为动态输入。
2. 统一后端服务：基于 Flask Blueprint 组织接口模块，利用 PostgreSQL 存储多类业务数据。
3. 多维分析建模：从实时记录中生成准点率、健康度、告警、碳排放与客流等衍生指标。
4. 前端统一呈现：通过 Vue 3 单页应用承载数据浏览、图表分析、地图展示与后台管理。
5. 工程化保障：使用配置管理、自动 schema 初始化、权限控制、审计与测试脚本提升系统可靠性。

## 第2章 相关技术与理论基础

### 2.1 GTFS 静态数据标准

GTFS 是描述公共交通静态运营信息的开放标准，核心由多个 `.txt` 文件组成，并通过压缩包方式发布[1-2]。在最基础的场景下，`agency.txt`、`routes.txt`、`trips.txt`、`stops.txt`、`stop_times.txt`、`calendar.txt` 与 `calendar_dates.txt` 构成了公交服务表达的主干。对于本文系统而言，GTFS 的价值主要体现在三个方面。

第一，GTFS 提供了统一的数据语义。公交线路、班次、站点、时刻表、轨迹和票价等对象都有明确字段定义，使得系统可以不依赖具体城市数据格式，而围绕统一模型设计数据库表结构和查询接口。

第二，GTFS 具有良好的扩展兼容性。项目中的旧金山湾区数据包含 `route_attributes`、`calendar_attributes`、`rider_categories` 等扩展文件，悉尼和纽约又具有各自特点。后端导入器通过“读取数据库实际列并忽略 CSV 中未知列”的方式，对这种异构扩展提供了兼容支持。

第三，GTFS 天然适用于课程项目中的规范化建模。因为其数据文件之间存在清晰的主外键关系，所以可以直接映射为关系型数据库结构。例如，`routes` 与 `agency` 关联，`trips` 依赖 `routes`，`stop_times` 同时依赖 `trips` 和 `stops`。这种依赖关系决定了导入顺序，也为后续的联合查询、统计分析和地图展示提供了基础。

### 2.2 GTFS-Realtime 动态数据标准

GTFS-Realtime 在静态时刻表基础上补充动态运行信息[3]。其常见消息类型包括车辆位置、班次更新和服务告警，通常通过 Protocol Buffers 序列化后由 HTTP 接口提供。对公交智能分析平台而言，静态 GTFS 解决的是“计划如何运行”的问题，GTFS-Realtime 解决的是“当前实际运行到什么程度”的问题。

本文系统主要利用 GTFS-Realtime 中的车辆位置与班次更新两类信息。车辆位置数据用于构建 `realtime_vehicle_positions` 表，服务于实时车辆监控、地图展示和历史回放；班次更新中的时刻偏差用于生成 `realtime_delay_records`，进一步支撑线路、站点和系统级准点率分析。由于旧金山湾区、悉尼和纽约的数据接口形式存在差异，后端在 `PunctualityDataService` 中采用地区到 fetcher 的映射配置，将接口差异封装在数据采集层，业务层只面向统一的延误记录对象进行处理。

### 2.3 Flask 与 RESTful 服务设计

Flask 是轻量级 Python Web 框架，适合以较少抽象快速构建面向接口的服务[4]。官方文档指出，Blueprint 机制能够将大型应用拆分为多个模块，便于在同一应用中组织不同前缀和职责的接口[4]。本项目的后端入口位于 `backend/api/app.py`，在应用初始化阶段注册了认证、GTFS 查询、实时监控、准点率、用户功能、管理后台、分析工具、告警健康度和碳排放等多个 Blueprint，形成了清晰的分层结构。

采用 Flask 的原因主要包括以下几点。其一，项目核心需求以 REST API 为主，不依赖复杂服务端模板渲染，因此轻量框架更适合。其二，项目中包含较多定制化 SQL 和数据处理流程，使用 Flask 可以直接控制请求、响应、异常处理和数据库访问逻辑。其三，Flask 与 Python 数据处理生态结合紧密，便于编写导入脚本、采集脚本、测试脚本和指标计算脚本。

在接口设计上，系统遵循统一的 JSON 返回结构，通过 `success_response` 与 `error_response` 包装结果，减轻前端解析复杂度。同时，接口以资源与业务动作为主线组织路径，例如 `/api/routes`、`/api/stops`、`/api/punctuality/routes`、`/api/planner/transfer` 等。经统计，当前仓库在 `backend/api` 目录下已定义约 86 个路由处理函数，基本覆盖公交信息平台的核心业务场景。

### 2.4 Vue 3 前端技术体系

Vue 3 提供声明式、组件化的前端开发模式，能够高效构建单页应用和复杂交互界面[5]。项目采用 Vue 3 的 Composition API 与 `<script setup>` 语法，配合 Pinia、Vue Router 和 Element Plus 组织前端工程。

从工程结构看，`frontend/src/views` 中保存了 31 个页面视图，`frontend/src/components` 中封装了搜索框、通知铃铛、订阅按钮等通用组件，`frontend/src/stores` 中实现了认证、线路、站点、收藏、通知和主题等状态管理逻辑。路由文件 `frontend/src/router/index.js` 对页面进行集中注册，并在 `beforeEach` 中完成登录态与管理员权限校验，在 `afterEach` 中上报页面访问审计日志。该设计将页面导航、权限判断和用户行为追踪整合到统一入口，体现了前端工程化思路。

Vue 3 适用于本项目的另一个重要原因在于其组件生态完善。公交信息平台中存在大量表格、图表、地图、筛选器和分页器，使用组件化方式可以有效复用交互模式。例如首页 `Home.vue` 将系统功能分为“线路与站点”“出行工具”“准点率分析”等多个区域，通过统一卡片交互引导用户进入不同模块，这一组织方式与后台分析类应用高度契合。

### 2.5 PostgreSQL 关系数据库

PostgreSQL 是功能完备的开源对象关系数据库系统，支持事务、外键、视图、索引和丰富的数据类型[6]。这些能力与 GTFS 数据的关系建模需求高度吻合。因为 GTFS 数据存在多表强关联关系，且系统还需要管理 JSON、日志、统计结果和用户数据，所以 PostgreSQL 是比轻量级嵌入式数据库更合适的选择。

本项目中的 PostgreSQL 主要承担三类任务。第一类是存储 GTFS 主数据，例如 `routes`、`stops`、`trips`、`stop_times` 等。第二类是存储动态采集与分析结果，例如 `realtime_delay_records`、`route_daily_punctuality`、`hourly_punctuality_stats`、`realtime_vehicle_positions` 等。第三类是存储业务扩展和运维信息，例如 `user_favorites`、`notifications`、`audit_logs`、`api_call_logs`、`data_quality_checks`、`route_health_scores` 等。

仓库中的数据库模块通过 `core/db.py` 封装了简单连接池和常用查询函数，包括 `execute_query`、`execute_query_one`、`execute_write` 和 `execute_count`。这种轻量封装避免了在课程项目中引入过重 ORM，同时保留了对 SQL 的直接控制能力，便于根据 GTFS 查询和统计需求编写针对性较强的语句。

### 2.6 Element Plus、ECharts 与 Leaflet

Element Plus 是基于 Vue 3 的组件库，提供表单、表格、对话框、分页、通知、布局等常用组件[7]。对于公交信息平台这类管理与分析并重的系统，成熟组件库可以显著降低基础交互的开发成本，并保持界面结构的一致性。本项目中登录页、数据表格、筛选条件、统计卡片和后台管理表单大量依赖 Element Plus 组件体系。

ECharts 适合展示折线图、柱状图、饼图、热力分布和趋势变化信息，特别适用于准点率趋势、小时分布、健康度构成和告警统计等分析场景[9]。Leaflet 则提供轻量地图能力，适合在 Web 页面中叠加线路轨迹、站点坐标、车辆位置和热力图层[8]。公交业务天然依赖空间信息，因此地图可视化是系统的重要组成部分。项目通过路线地图、站点详情地图、车辆回放地图和站点热力图，使抽象数据具备空间解释能力。

### 2.7 准点率评价理论

公交运行服务质量中，准点率是最核心、最直观的评价指标之一。它反映车辆在计划时刻附近到站或发车的稳定程度。准点率本身并不是孤立存在的，它通常与平均延误、最大延误、不同时间段表现和不同线路表现共同构成服务评价体系[10]。

在本文系统中，延误值以秒为单位记录，正值表示延误，负值表示提前。系统将准点判断阈值设计为可配置项，默认采用以下规则：提前超过 60 秒记为提前；绝对延误不超过 120 秒记为准点；延误在 120 秒至 300 秒之间记为延误；延误超过 300 秒记为严重延误。基于这一阈值配置，可以定义线路准点率如下：

```text
P_r = N_on / N_total × 100%    （2-1）
```

式中，`P_r` 表示线路准点率，`N_on` 表示准点样本数，`N_total` 表示统计周期内总样本数。

平均延误时间可表示为：

```text
\bar{d} = (1 / N_total) × Σ d_i    （2-2）
```

式中，`d_i` 表示第 `i` 条延误记录的到站延误秒数。当 `d_i` 为负时，代表车辆早于计划时刻到达。除准点率外，系统还对提前率、延误率、严重延误率、最大延误和最小延误进行聚合，以更全面刻画线路或站点的运行状态。

### 2.8 公交路径规划与可达性分析基础

路径规划是公交信息系统中的常见难点。与普通道路导航不同，公交路径不仅涉及地理距离，还涉及时刻表、站点停靠顺序、换乘次数和候车时间等因素。经典研究表明，公共交通网络中的路径搜索需要兼顾到达时间与换乘次数等多目标因素[11]。在大型城市网络中，直接把整个系统展开为普通图并执行最短路搜索，往往会导致状态空间过大。

本项目的换乘规划并未完全采用 RAPTOR 等成熟算法，而是依据课程项目规模和已有数据库结构，采用“按线路展开，每条线路只取一个代表班次”的轻量化策略。该方法虽然在全局最优性和复杂约束处理方面弱于成熟研究算法，但具有实现简单、结果可解释、对中小规模数据友好的优点。站点可达性分析则进一步基于站点前沿扩展和限定时间上界，统计某起点站在给定时间预算内的可到达站点集合。这类方法适合在教学场景中展示“由时刻表网络生成空间覆盖能力”的概念。

### 2.9 Pinia 状态管理与 Vite 构建工具

Pinia 是 Vue 官方推荐的新一代状态管理库，相较于 Vuex，其 API 更加简洁，对 TypeScript 和 Composition API 的支持也更为完善。本项目中，`authStore`、`regionStore`、`routeStore`、`stopStore`、`favoriteStore`、`notificationStore`、`punctualityStore`、`themeStore` 和 `appStore` 九个 store 分别承担认证、地区选择、线路缓存、站点缓存、收藏管理、通知未读统计、准点率数据缓存、主题切换和全局应用状态等职责。Store 之间通过组合式函数相互调用，例如 `authStore` 在登录成功后主动触发 `favoriteStore.fetchFavorites()` 和 `notificationStore.fetchUnreadCount()`，形成了松耦合的跨模块协作模式。

Vite 则是现代前端构建工具，其特点是以原生 ES Module 为基础实现开发时按需编译，显著提升冷启动和热更新速度。本项目前端开发服务器默认运行于 `5173` 端口，结合 Vue 3 单文件组件机制，能够在保存文件后在 500 毫秒级别内完成模块热替换，保证了开发效率。

### 2.10 Axios 与前后端通信机制

Axios 是前端常用的 Promise 风格 HTTP 客户端，本项目在 `frontend/src/api/index.js` 中创建了统一的 Axios 实例，并集中配置了基础 URL、超时时间、凭证携带和请求/响应拦截器。请求拦截器负责向参数中自动附加 `region` 字段，以及为需要登录的接口注入 `Authorization` 请求头；响应拦截器则对后端返回的统一 JSON 结构进行解包处理，将 `data` 字段直接返回给业务调用方，并在遇到 401 未授权时自动跳转登录页。该设计使业务代码可以专注于数据加工，而无需重复编写地区参数拼接、令牌注入和错误处理逻辑。

需要指出的是，由于响应拦截器已经完成解包，所有调用者都应直接使用返回值，不应再访问 `response.data.data`，否则会导致二次解包异常。此类约定性细节被记录在项目根目录的 `CLAUDE.md` 中，作为开发规范的一部分。

### 2.11 Protocol Buffers 与 GTFS-Realtime 解码

GTFS-Realtime 消息通常以 Protocol Buffers 二进制格式通过 HTTP 接口提供[12]。Protocol Buffers 是 Google 推出的跨语言结构化数据序列化协议，与 JSON 相比具有更高的编解码效率和更小的传输体积。本项目通过 `gtfs-realtime-bindings` Python 库解析二进制消息，将其转换为可直接访问的对象树，并进一步映射到内部 `DelayRecord` 与车辆位置记录结构。对不同地区的接口差异，系统在 `GTFSDataFetcher`、`MTADataFetcher` 和 `TfNSWDataFetcher` 三个类中进行封装，上层业务只面向统一的数据模型处理。

### 2.12 本章小结

本章介绍了系统实现所依赖的核心技术与理论基础，包括 GTFS 与 GTFS-Realtime 标准、Flask 后端服务、Vue 3 前端体系、PostgreSQL 数据库、Element Plus/ECharts/Leaflet 可视化工具、Pinia 状态管理与 Vite 构建工具、Axios 通信机制和 Protocol Buffers 序列化协议，以及准点率评价与公交路径分析的基础方法。可以看到，本文系统并不是对单一技术的简单堆叠，而是在交通标准、Web 架构、数据库设计和业务分析方法之间建立了清晰联系。各项技术选型既彼此独立又相互配合，构成了一套兼顾学习成本与工程实用性的完整技术体系。后续章节将在此基础上展开需求分析与系统设计。

## 第3章 系统需求分析

### 3.1 需求分析目标

需求分析的目的在于明确系统“为谁服务、解决什么问题、在何种约束下实现”。由于本项目既面向普通乘客，也面向系统管理员和开发维护者，因此需求分析不能只关注单一用户的查询体验，还必须兼顾数据接入、分析处理、权限控制、日志审计和运维监控等后台需求。

结合仓库中已实现的功能与页面，本文将系统需求分为乘客服务需求、公交运行分析需求、平台治理需求和工程运维需求四个层面。其中，乘客服务需求强调查询与辅助决策，运行分析需求强调数据聚合与洞察输出，平台治理需求强调角色、通知、审计与后台管理，工程运维需求则关注配置、脚本、测试和部署便利性。

### 3.2 业务场景分析

#### 3.2.1 乘客场景

乘客在实际出行过程中，通常需要完成以下任务：查看线路和站点信息、确认班次和运营时间、观察实时车辆位置、判断当前线路运行是否稳定、在多个候选方案中选择更合适的线路、规划起终点换乘方案，以及在日常使用中收藏常用线路并接收告警通知。传统查询式系统往往只满足前两项，而本文系统尝试将上述任务纳入同一平台。

例如，当乘客打开首页后，可以从“浏览线路”“查找站点”“实时监控”“线路准点率”“换乘规划”“站点可达性”“线路对比”“我的收藏”等模块进入不同业务流程。如果乘客已经登录，还可以通过订阅某条线路，在准点率低于阈值时接收到站内通知。这种设计体现了从“信息浏览”到“持续服务”的转变。

#### 3.2.2 管理员场景

管理员除拥有普通用户可见功能外，还需要处理系统管理任务。例如查看数据库容量与各表大小、观察第三方接口调用成功率、掌握数据导入与更新情况、管理用户账户、查看审计日志、发布系统公告、查看数据质量检查结果、处理异常告警和触发线路健康度重算等。若系统缺乏这些功能，即便前端展示效果良好，也难以支撑真实环境中的长期运行。

#### 3.2.3 开发与维护场景

开发维护者需要快速启动系统、导入数据、检查接口、定位故障，并在增加新模块时尽可能少地改动已有基础设施。为满足这些需求，项目提供了 `start.sh` 一键启动脚本、`schema_bootstrap.py` 自动补表机制、`config.py` 配置加载器和多份脚本式测试文件。这些需求虽然不直接面向最终用户，但对毕业设计项目的完整性非常关键。

### 3.3 用户角色分析

系统当前涉及三类主要角色。

1. 未登录访客。系统对大部分页面采用登录校验，因此未登录用户主要访问登录页，不具备业务操作权限。
2. 普通用户。登录后可访问线路、站点、地图、实时监控、准点率分析、换乘规划、可达性分析、收藏、通知、订阅、碳排放和推荐等功能。
3. 管理员。除拥有普通用户权限外，还可访问用户管理、审计日志、数据库统计、接口健康、数据质量和公告发布等后台模块。

前端路由守卫使用 `localStorage` 中的 `auth_token` 与 `auth_role` 判断访问权限，后端则通过请求中的登录态识别当前用户并在需要时调用 `require_admin` 完成管理员校验。用户角色模型较为清晰，适合课程项目展示权限分层思想。

### 3.4 功能需求分析

#### 3.4.1 GTFS 静态数据管理需求

系统需要支持从 GTFS ZIP 文件或目录中导入静态数据，并能够适应不同地区之间文件内容和扩展字段的差异。导入过程中需要保证表依赖关系正确，避免因外键顺序错误导致导入失败。系统还应支持按地区清理旧数据，而不是直接清空整个数据库，以便在多地区共存场景下执行局部更新。

#### 3.4.2 基础查询需求

平台需提供线路、站点、班次、日历、形状轨迹、运营机构和统计信息查询能力。查询接口应支持按地区筛选、分页或限制数量，并能为前端地图、列表和详情页提供稳定的数据结构。此类需求构成系统最基础的数据服务层。

#### 3.4.3 实时监控需求

系统需要获取 GTFS-Realtime 车辆位置与班次更新信息，实现实时车辆位置展示、实时延误记录展示、活跃车辆数量统计、延误线路统计以及历史轨迹回放。考虑到第三方接口可能不可用，系统还需要具备重试与模拟数据降级能力，以避免演示环境完全失效。

#### 3.4.4 准点率分析需求

准点率分析需求是本项目的核心。系统应能够从实时延误记录中形成系统概览、线路排名、站点排名、时段分布、趋势总览以及线路和站点的明细统计。同时，准点率阈值需要可配置，以适应不同城市或不同分析口径的要求。为了便于长期观察，统计结果不应仅停留在内存计算，而应落库保存。

#### 3.4.5 出行辅助需求

面向乘客的辅助功能主要包括换乘规划、站点可达性分析、线路对比、数据导出和智能推荐。换乘规划需求强调从起点站到终点站的候选方案生成；可达性需求强调给定站点和时间预算时的覆盖范围；线路对比强调对多条候选线路的关键指标进行横向比较；数据导出强调将查询结果转为 CSV、Excel 或 PDF；智能推荐则尝试结合用户收藏和访问频率生成个性化结果。

#### 3.4.6 用户服务需求

用户服务需求包括注册、登录、登出、当前用户信息、收藏、订阅、通知、绿色出行记录与排行榜等。其中，收藏与订阅构成用户个性化服务基础，通知系统负责将告警和公告传递给用户，碳排放记录则增强了系统的公共服务教育属性。

#### 3.4.7 管理与运维需求

后台管理需求包括用户管理、公告发布、数据库统计、接口健康监控、数据时效性展示、审计日志查询、数据质量看板、异常告警处理和线路健康度计算等。这些需求表明，本系统不是单纯的“前台信息查询网站”，而是面向完整业务链路的综合平台。

### 3.5 非功能需求分析

#### 3.5.1 可用性需求

系统需要具备较好的交互一致性和学习成本可控的界面组织方式。首页应能够清晰展示主要功能入口，列表页需要支持筛选和分页，图表页需要突出关键指标，地图页需要具备足够的空间感知能力。前端采用组件库和统一布局正是为了满足该需求。

#### 3.5.2 可维护性需求

系统应当便于新增功能与地区。后端通过 Blueprint 划分模块，数据库通过多个 schema SQL 文件组织扩展能力，前端通过路由、API 模块和 stores 分离状态。`ensure_feature_schemas()` 能够在应用启动时自动补齐部分扩展表，降低新增功能的部署门槛。

#### 3.5.3 可扩展性需求

随着业务扩展，系统可能需要接入新地区、新型分析模块或新的第三方接口。为此，数据表设计应尽可能引入 `region` 字段统一隔离，数据采集层应通过 fetcher 映射封装不同来源差异，前端页面组织应允许新增导航模块。当前系统已经具备这一雏形。

#### 3.5.4 安全性需求

系统需保证基本登录认证、角色校验和关键操作追踪。项目中密码使用 `pbkdf2_hmac` 进行哈希处理，管理员接口需要显式校验权限，用户关键操作和管理员操作会写入 `audit_logs` 表。这些机制为课程项目提供了必要的安全边界。

#### 3.5.5 可测试性需求

毕业设计项目应具备可验证性。仓库中提供 `test_api_quick.py`、`test_punctuality.py`、`check_db.py`、`check_data_detail.py`、`test_new_features.py` 等脚本，便于从接口、计算逻辑和数据库视角进行检查。虽然这不是完整的自动化测试框架，但已经满足项目级脚本验证需求。

### 3.6 数据需求分析

系统涉及的数据可以分为五类。

第一类是 GTFS 静态主数据，包括线路、站点、班次、时刻表、轨迹、票价和服务日历，是所有查询与分析的基础。

第二类是 GTFS-Realtime 动态数据，包括车辆位置、班次更新时间和服务告警，是实时监控和准点率分析的基础。

第三类是用户业务数据，包括用户账户、收藏、订阅、通知和碳排放记录，支撑个性化服务。

第四类是分析衍生数据，包括线路日准点率、站点日准点率、小时准点率、系统概览、健康度评分、客流预测和异常告警等，支撑平台分析能力。

第五类是运维与治理数据，包括 API 调用日志、数据更新日志、审计日志和数据质量检查记录，支撑后台管理与平台治理。

数据需求的复杂性说明，平台必须采用关系数据库加分模块建表的方式，而不能只依靠单一 JSON 文件或简单缓存完成所有业务。

### 3.7 可行性分析

#### 3.7.1 技术可行性

从技术栈看，Python、Flask、Vue 3 和 PostgreSQL 都是成熟、文档完善、学习成本适中的技术方案[4-7]。GTFS/GTFS-Realtime 本身又是公开标准[1-3]，使得项目在技术实现上不存在明显障碍。地图和图表可视化也已有成熟生态支持，因此整体技术方案可行。

#### 3.7.2 经济可行性

项目主要依赖开源软件和公开数据，不需要额外采购商业服务即可完成开发与本地部署。对于毕业设计而言，该方案具有较低成本。

#### 3.7.3 实施可行性

项目采用模块化设计，可分阶段完成。仓库当前已经实现多项功能，并提供启动脚本、导入脚本和测试脚本，说明系统具备较好的实施基础。新增模块也能够在既有架构下继续演进。

### 3.8 用例分析

为更直观描述系统典型使用过程，本节以若干用例为例对需求进行补充说明。

**用例一：普通用户查询线路准点率**。前置条件为用户已登录。主事件流为：用户从首页进入“线路准点率”页面，系统按当前地区加载线路排名表；用户可按线路编号或名称搜索，系统返回匹配列表；用户点击某条线路后进入线路准点率详情页，系统加载该线路近 7 天的准点率趋势、延误分布和站点排名；用户若认为该线路值得长期关注，可直接在详情页点击“订阅”按钮，系统弹出阈值输入框，用户填写准点率阈值后提交，系统将订阅记录写入 `user_subscriptions` 表。例外流包括：若当前地区无准点率数据，系统提示“暂无数据”；若订阅失败，系统给出错误提示。

**用例二：管理员处理告警**。前置条件为管理员已登录。主事件流为：管理员进入“告警中心”页面，系统加载当前活跃告警列表；列表按严重程度倒序排列，`critical` 告警以红色高亮；管理员点击某条告警查看详情，系统展示告警类型、触发实体、触发时间和详情数据；管理员确认告警已被现场处理后，点击“标记为已解决”按钮，系统将 `resolved_at` 字段更新为当前时间，并从活跃告警列表中移除该条。例外流包括：若告警已被其他管理员处理，系统给出提示并刷新列表。

**用例三：导入新地区 GTFS 数据**。前置条件为维护者具备数据库访问权限。主事件流为：维护者将新地区 GTFS ZIP 文件放入 `gtfs_data/` 目录；执行 `python3 backend/data_acquisition/gtfs_importer.py --zip <文件> --region <标识> --clean`；导入器按 `TABLE_ORDER` 顺序读取 GTFS 文件并批量写入数据库；导入结束后输出每张表的记录数以供核对；若 `--region` 在 `regions` 表中尚不存在，导入器会提前创建该地区记录。例外流包括：若 ZIP 文件格式错误或缺失必须文件，导入器中止并给出明确错误信息；若某条记录触发外键冲突，导入器抛出异常并回滚事务。

### 3.9 需求优先级与实现取舍

考虑到毕业设计项目的时间和人力约束，在需求分析阶段需要对各项功能进行优先级排序。本项目将需求分为“核心必做”“重要推荐”“可选增强”三类。核心必做类涵盖 GTFS 导入、基础查询、实时监控、准点率分析、用户认证和管理后台，这些功能构成系统主干；重要推荐类包括收藏订阅、通知、换乘规划、可达性分析、数据导出和审计日志，它们显著提升系统可用性；可选增强类包括健康度评分、异常告警、碳排放、客流预测、智能推荐和数据质量审查，这些功能扩展了系统的分析深度。

最终实现过程中，三类功能均已完成主体能力。其中核心必做类达到了“完整闭环”标准，重要推荐类达到了“稳定可用”标准，可选增强类达到了“可演示并具备扩展空间”标准。这种分层处理方式既保证了核心能力的可靠性，也为系统留出了持续优化的空间。

### 3.10 本章小结

本章从用户角色、业务场景、功能需求、非功能需求和数据需求五个层面对系统进行了分析。需求分析结果表明，目标系统不仅需要提供基础 GTFS 查询和实时监控能力，还需要覆盖准点率分析、出行辅助、个性化服务和后台治理等多个方面。因此，后续系统设计必须兼顾数据标准化、模块化架构、权限控制和工程可维护性，才能支撑这些复合需求。

## 第4章 系统总体设计

### 4.1 设计目标与设计原则

在上一章需求分析基础上，本文将系统总体设计目标归纳为以下五点。

1. 统一数据基础。以 GTFS/GTFS-Realtime 为核心构建统一数据模型，避免不同模块各自维护孤立结构。
2. 支撑多类业务。系统不仅要处理查询与展示，还要支撑分析、管理和用户服务。
3. 保持模块化。后端接口、数据库扩展、前端页面和状态管理应能够独立演进。
4. 兼顾实现成本与工程性。系统面向毕业设计项目，既要具备完整性，也要控制技术复杂度，避免为追求“工业级完备”而牺牲可实现性。
5. 为扩展预留空间。新增地区、新功能和新数据源时，应尽量复用已有架构而不是大幅推翻重构。

围绕上述目标，系统设计遵循以下原则。

第一，标准优先原则。凡是能够由 GTFS 标准表达的静态对象，尽量直接映射到数据库与接口层，减少不必要的二次抽象。

第二，前后端解耦原则。前端仅通过 RESTful 接口获取数据，后端负责数据组织与业务处理，从而降低展示层与数据层的耦合度。

第三，分层组织原则。将数据采集、业务逻辑、接口层、状态层和视图层分离，既方便定位问题，也便于后续扩展。

第四，结果可解释原则。无论是准点率统计、换乘规划还是健康度评分，都应保持计算逻辑可追溯、指标含义明确，避免黑箱化设计。

第五，渐进增强原则。在基础查询稳定可用的前提下逐步叠加实时监控、分析工具、用户体系和运维功能，形成可持续迭代的系统结构。

### 4.2 系统总体架构

#### 4.2.1 架构模式选择

系统采用典型的 B/S（Browser/Server）架构和前后端分离模式。浏览器端负责交互、可视化和状态呈现，服务端负责数据访问、业务计算和权限控制，数据库负责持久化存储。这种模式相较于单体模板渲染架构具有更好的前后端分工清晰度，也更适合地图、图表和动态筛选较多的公交信息系统。

从部署形式看，项目在本地开发环境下通过 `start.sh` 脚本启动 PostgreSQL、Flask 后端和 Vite 前端，其中后端默认使用 `5001` 端口，前端使用 `5173` 端口。该方式足以满足课程项目开发、联调与演示需求。

#### 4.2.2 逻辑架构划分

系统总体逻辑架构可概括为四层。

```text
表示层：Vue 3 + Element Plus + ECharts + Leaflet
接口层：Flask Blueprint + RESTful API
业务层：数据导入、实时采集、准点率、换乘、可达性、告警、健康度等
数据层：PostgreSQL（GTFS 主数据 + 分析数据 + 用户数据 + 运维数据）
```

表示层负责页面布局、图表渲染、地图交互和表单操作；接口层负责接收请求、校验参数并返回统一 JSON；业务层负责核心计算和数据组装；数据层负责持久化存储及基于 SQL 的联合查询和聚合分析。由于项目并未引入专门消息队列或独立缓存层，因此整体架构保持相对简洁，但仍能覆盖完整业务链路。

#### 4.2.3 模块划分

依据仓库目录结构，可将系统划分为以下模块。

1. 数据采集与导入模块：位于 `backend/data_acquisition/`，包括 GTFS 导入器和不同地区的实时数据获取器。
2. 核心业务模块：位于 `backend/business_logic/`，包括准点率计算、换乘规划、可达性分析和速度计算等。
3. 服务与脚本模块：位于 `backend/services/` 和 `backend/scripts/`，负责定时采集、模拟数据、评分计算、数据检查与脚本启动。
4. API 接口模块：位于 `backend/api/`，面向前端暴露所有业务能力。
5. 用户认证与权限模块：位于 `backend/auth/`，提供注册、登录、默认管理员初始化和 token 校验。
6. 前端视图与状态模块：位于 `frontend/src/` 下的 `views`、`components`、`stores`、`api` 与 `router`。
7. 数据库存储模块：位于 `backend/database/`，通过主 schema 与多个扩展 schema 组织 38 张表。

这种模块划分与需求结构基本对应，有利于维持系统的职责边界。

### 4.3 后端架构设计

#### 4.3.1 应用入口设计

`backend/api/app.py` 是后端主入口。该文件完成以下职责：创建 Flask 应用、开启跨域支持、注册所有 Blueprint、在请求前初始化数据库连接池和默认用户、自动执行扩展 schema 建立，以及定义统一的 404 和 500 错误处理逻辑。这样做的优点是，后端在第一次请求到达前即可尽量完成环境准备，降低由于遗漏建表或默认账号缺失带来的启动问题。

在 Blueprint 组织上，当前系统注册了 `auth_bp`、`gtfs_bp`、`realtime_bp`、`punctuality_bp`、`user_features_bp`、`admin_bp`、`health_alerts_bp`、`analysis_bp` 和 `carbon_bp` 九类核心模块。每个模块围绕相对稳定的业务边界构建，例如实时监控模块专注于车辆位置与延误，管理后台专注于数据库和运维统计，分析模块专注于换乘、可达性、客流预测和推荐。

#### 4.3.2 数据访问设计

系统没有使用重量级 ORM，而是以 `core/db.py` 为核心，提供连接池初始化与四类基础数据库操作函数。这一设计有以下优势。

1. GTFS 查询往往需要复杂 SQL，手写 SQL 更便于控制联表、聚合和排序逻辑。
2. 对课程项目而言，自定义轻量封装更容易理解和调试。
3. 数据导入、统计聚合和后台报表等场景对 SQL 灵活度要求较高，直接 SQL 能减少抽象损耗。

当然，这种设计也有代价，例如类型约束、模型复用和迁移管理能力不如成熟 ORM 完整。但考虑项目规模和实现目标，该权衡是合理的。

#### 4.3.3 配置与初始化设计

配置模块 `backend/core/config.py` 采用“环境变量 > `config.local.json` > `config.json`”的优先级策略，兼顾本地配置与部署灵活性。不同地区的数据接口密钥通过统一方法 `get_api_key(region)` 获取，准点率相关默认配置也由配置模块提供。这一设计避免了把 API Key 写死在代码中，符合基本安全要求。

扩展表初始化则由 `backend/core/schema_bootstrap.py` 负责。其在启动时读取 `data_quality_schema.sql`、`health_score_schema.sql`、`alert_schema.sql`、`carbon_schema.sql` 和 `flow_prediction_schema.sql`，并执行补充迁移语句。该机制的意义在于，当项目功能逐步扩展时，不需要依赖手工执行每一个 SQL 文件即可在运行时完成必要的补表操作。

### 4.4 前端架构设计

#### 4.4.1 页面组织设计

前端采用单页应用模式。`frontend/src/router/index.js` 中定义了 31 个页面路由，覆盖登录、首页、线路、站点、地图、时刻表、历史回放、准点率、收藏、换乘规划、可达性分析、线路对比、数据导出、管理后台、用户管理、审计日志、数据质量、健康度、告警、碳排放、客流预测和推荐等视图。页面以业务场景为单位组织，而不是按数据库表组织，有利于符合用户认知。

首页 `Home.vue` 采用功能卡片聚合方式，将系统能力分为多个功能分区。该设计兼具导航与概览作用，适合功能较多的后台式 Web 应用。用户无需记忆全部菜单结构，即可通过卡片化入口进入常用模块。

#### 4.4.2 状态管理设计

Pinia 用于维护跨页面状态，例如认证信息、收藏列表、通知未读数、地区选择和主题切换等。以 `authStore.js` 为例，系统将 token、用户名和角色信息保存在响应式状态和 `localStorage` 中，并在登录成功后主动拉取收藏和通知数据。这样既避免了页面间重复请求，也使登录态在浏览器刷新后仍可保持。

#### 4.4.3 权限与审计设计

路由守卫在进入受保护页面时验证 token 是否存在，并对管理员页面检查 `role` 是否为 `admin`。登录成功后，前端的 `afterEach` 钩子还会调用审计接口，异步记录页面访问行为。由于上报逻辑不阻塞页面渲染，因此不会明显影响用户体验。该机制体现了“前端负责触发，后端负责落库”的审计设计思路。

### 4.5 数据库总体设计

#### 4.5.1 数据库设计思路

数据库设计是本系统的关键。不同于只包含基础实体的教学示例库，本文系统需要同时支持：

1. GTFS 主数据；
2. GTFS-Realtime 落库数据；
3. 准点率与健康度等分析结果；
4. 用户账户、收藏、订阅和通知；
5. 审计、日志、数据质量与运维统计。

为解决多数据源共存问题，系统在大多数核心表中引入 `region` 字段，并将其纳入主键或联合唯一约束。例如 `routes` 主键为 `(region, route_id)`，`stops` 主键为 `(region, stop_id)`。这种设计的优点在于，多个城市可以共享相同表结构，但数据逻辑上保持隔离，同时又便于前端通过统一接口以 `region` 参数切换数据视角。

#### 4.5.2 主数据表设计

`schema.sql` 定义了 GTFS 主数据核心表，包括 `regions`、`agency`、`routes`、`route_attributes`、`directions`、`stops`、`calendar`、`calendar_attributes`、`calendar_dates`、`shapes`、`trips`、`stop_times`、`rider_categories`、`fare_attributes`、`fare_rider_categories`、`fare_rules`、`feed_info` 和 `attributions`。这些表完整映射了 GTFS 主体结构，并在部分表中兼容旧金山湾区扩展字段。

在关系组织上，`routes` 依赖 `agency`，`trips` 依赖 `routes`，`stop_times` 同时依赖 `trips` 和 `stops`，`shapes` 与 `trips` 通过 `shape_id` 形成路径映射。由于公交时刻表查询和地图可视化都依赖这些关系，因此主数据表设计直接决定了后续接口能力的上限。

#### 4.5.3 分析与业务扩展表设计

准点率相关表由 `punctuality_schema.sql` 定义，包括 `realtime_delay_records`、`route_daily_punctuality`、`stop_daily_punctuality`、`hourly_punctuality_stats`、`realtime_vehicle_positions`、`system_punctuality_overview` 和 `punctuality_config`。这些表将原始实时数据与聚合分析结果分层保存，既保留明细数据，也支持快速统计查询。

管理与运维表包括 `api_call_logs`、`data_update_logs`、`audit_logs` 等，用于记录第三方接口健康、导入历史和关键操作。用户业务表包括 `users`、`user_favorites`、`user_subscriptions`、`notifications` 等。扩展分析表则包括 `data_quality_checks`、`data_quality_issues`、`route_health_scores`、`anomaly_alerts`、`route_distances`、`user_carbon_records` 和 `stop_flow_predictions`。从设计结果看，系统数据库已具备明显的“主数据层 + 分析层 + 业务层 + 运维层”分层特征。

#### 4.5.4 索引设计

为了提升查询与统计效率，系统在准点率和实时数据表上建立了较多索引，例如 `realtime_delay_records` 的地区、线路、站点、时间戳索引，以及 `route_daily_punctuality`、`stop_daily_punctuality`、`realtime_vehicle_positions` 和 `system_punctuality_overview` 的常用查询字段索引。对公交场景而言，时间、线路和站点是最核心的过滤维度，因此索引设计围绕这些字段展开是合理的。

### 4.6 接口体系设计

#### 4.6.1 接口分组

根据业务职能，系统接口可分为以下类别。

1. 基础数据接口：地区、机构、线路、站点、班次、时刻表、形状、日历和统计。
2. 实时监控接口：车辆位置、延误记录、实时汇总、历史轨迹和手动同步。
3. 准点率接口：概览、线路、站点、小时统计、趋势、明细和配置。
4. 分析工具接口：换乘规划、站点可达性、客流预测、热力图和智能推荐。
5. 用户功能接口：注册登录、收藏、订阅、通知和碳排放。
6. 管理接口：数据库统计、接口健康、数据时效性、用户管理、审计日志和数据质量。
7. 扩展分析接口：健康度评分、告警统计和历史记录。

该分组方式与前端路由和后端 Blueprint 均保持一致，有利于降低理解和维护成本。

#### 4.6.2 接口风格

接口总体采用 RESTful 风格，路径以资源命名，参数通过查询字符串或 JSON 体传递，返回统一的 `code`、`message` 和 `data` 结构。这样可以让前端 API 模块在封装时保持一致。例如收藏接口支持 `GET/POST/DELETE` 不同方法，符合对同一资源执行查询、创建和删除操作的直觉。

#### 4.6.3 错误处理设计

后端在接口层对常见参数错误进行主动校验，并通过统一错误响应返回可读的中文消息。全局 404 和 500 错误处理进一步保证了异常情况下响应结构的统一性。对毕业设计项目而言，这种设计足以显著提升调试效率和用户可理解性。

### 4.7 安全与权限设计

#### 4.7.1 认证机制

认证模块通过用户名和密码完成登录验证。密码以 `pbkdf2_hmac('sha256', ...)` 进行哈希处理后存储，避免明文保存。登录成功后，后端生成随机 token 并保存在内存字典中，前端将 token 写入 `localStorage`。这种机制实现简单、演示友好，能够满足课程项目的基本认证需求。

但需要指出的是，当前 token 保存在后端内存中，服务重启后会失效，也缺乏过期控制与分布式会话支持。因此，本文将其定位为“开发与实验环境下的轻量认证方案”，后续若面向生产部署，应替换为基于数据库或 JWT 的更完整认证机制。

#### 4.7.2 授权机制

系统采用基于角色的权限控制方式。普通用户可访问大多数业务页面，管理员额外具备后台管理权限。无论前端路由守卫还是后端 `require_admin()` 校验，核心逻辑都是围绕 `role` 字段展开。这样既能防止前端绕过页面限制，也能在接口层再次确认权限边界。

#### 4.7.3 审计机制

审计机制通过 `record_audit_log()` 将关键操作、访问路径、用户标识和请求 IP 写入 `audit_logs`。项目还在前端路由切换后异步调用页面访问审计接口，形成对用户行为的基础追踪能力。对于管理后台类应用，这一能力不仅有助于排查问题，也体现了系统治理意识。

### 4.8 部署与运行设计

本项目的本地运行脚本 `start.sh` 负责以下工作：检查 PostgreSQL 是否运行，必要时调用 Homebrew 服务启动数据库；启动后端 Flask 服务并检查健康接口；启动前端 Vite 服务并检查开发服务器日志。脚本同时提供 `start`、`stop`、`status` 和 `restart` 四种操作模式，并通过 PID 文件管理进程状态。

这种脚本式部署方式虽然不属于完整的生产级运维方案，但对于毕业设计非常实用。它降低了前后端联调和演示门槛，也能帮助开发者快速判断问题是出在数据库、后端还是前端。

### 4.9 关键设计权衡

在总体设计过程中，存在若干关键权衡，本节对其逐一说明，以便于读者理解设计决策背后的考量。

第一，ORM 与原生 SQL 的取舍。主流 Python Web 项目常使用 SQLAlchemy 或 Peewee 等 ORM 框架屏蔽底层 SQL。但 GTFS 导入与准点率聚合存在大量多表联查、窗口函数和批量插入需求，使用 ORM 反而会引入额外抽象损耗。因此本项目选择以原生 SQL 为主、轻量连接池封装为辅的方案，在保持灵活性的同时避免性能陷阱。代价是部分代码存在 SQL 重复，未来若接入更多业务模块，可以考虑通过查询构建器或 SQL 模板进一步复用。

第二，单一后端进程与微服务化的取舍。当前项目将静态查询、实时采集、准点率分析、后台管理和用户服务全部集中在同一 Flask 应用中。这种方式便于部署和调试，适合毕业设计规模。但随着流量增长，实时采集的定时任务和用户交互请求共享同一线程池可能造成相互干扰。为此，系统将准点率数据采集封装为独立脚本 `start_punctuality_service.py`，允许以独立进程方式运行，为后续拆分留出空间。

第三，同步查询与异步任务的取舍。GTFS 数据导入和数据质量检查都可能耗时数十秒至数分钟，直接放入 HTTP 请求同步执行会导致前端长时间等待。当前版本采用“命令行脚本触发 + 后台管理接口可选异步调用”的方式，使耗时操作不阻塞前端交互。未来若引入 Celery 或 RQ 等任务队列，可以进一步规范这一模式。

第四，SPA 与 SSR 的取舍。单页应用有助于实现复杂交互和前端状态管理，但首屏加载时间较长且不利于搜索引擎爬取。考虑到本项目以登录后操作为主、对 SEO 无强需求，选择 SPA 是合适的。

### 4.10 模块依赖关系分析

为进一步说明系统各部分之间的协作关系，本节对核心模块依赖进行简要梳理。在后端层面，`data_acquisition` 模块负责从外部获取原始数据，是系统数据链路的起点；`business_logic` 模块接收采集到的数据并执行分析计算，属于系统的逻辑核心；`services` 模块将采集和分析能力组合为可长期运行的服务；`api` 模块在最外层暴露 HTTP 接口，并依赖 `core` 模块提供的数据库连接、配置、审计和自动建表能力；`auth` 模块则与 `core` 的审计能力紧密配合，形成登录校验和操作追踪闭环。

在前端层面，`api` 模块封装与后端的通信细节，是 `stores` 模块的依赖；`stores` 集中维护跨组件状态，被 `views` 和 `components` 直接消费；`router` 模块负责页面跳转，同时在守卫中调用 `authStore` 完成权限校验，并在切换后通过审计接口记录访问；`i18n` 模块为所有界面提供中英文文案；`utils` 模块承载导出、格式化等通用逻辑。这种自顶向下、逐层依赖的组织方式，使得每个模块都可以独立演进而不影响其它部分。

### 4.11 本章小结

本章从设计目标、系统架构、后端组织、前端结构、数据库模式、接口体系、安全权限和部署运行等方面对平台总体方案进行了阐述。总体来看，系统采用了标准化数据模型与模块化工程结构相结合的设计思路，既能覆盖多样化业务需求，也为后续章节中对各功能模块的详细实现提供了清晰框架。

## 第5章 系统详细设计与核心功能实现

### 5.1 GTFS 静态数据导入模块实现

#### 5.1.1 导入流程设计

GTFS 静态导入器位于 `backend/data_acquisition/gtfs_importer.py`。其核心流程为：建立数据库连接、根据参数确定导入来源（ZIP 或目录）、按依赖顺序依次读取 GTFS 文件、对每行数据追加 `region` 字段、生成批量插入 SQL、提交事务并输出导入结果。导入完成后，还可通过验证函数统计各表在指定地区下的记录数。

导入顺序由 `TABLE_ORDER` 明确给出，例如先导入 `agency`、`routes`、`stops`、`calendar` 等基础实体，再导入 `trips` 和 `stop_times`，最后导入票价与元数据相关表。之所以必须这样安排，是因为 `stop_times` 等表依赖上游主数据，一旦顺序错误就会触发外键冲突。

#### 5.1.2 多地区隔离实现

导入器在清理和写入时都显式携带 `region`。执行 `--clean` 时，系统不会直接 `TRUNCATE` 整张表，而是使用 `DELETE FROM table WHERE region = %s` 仅删除当前地区数据。这样旧金山和悉尼的数据可以长期共存于同一数据库中。对于需要统一前端界面但支持多个城市数据集的应用而言，这一设计非常关键。

#### 5.1.3 异构字段兼容实现

不同地区 GTFS 文件可能带有数据库中不存在的字段。为避免导入失败，导入器会先查询数据库实际列名，再只保留 CSV 中与数据库列匹配的字段，自动跳过额外字段。这一策略体现了“数据库结构主导，源数据兼容适配”的思想，能够有效提高跨地区数据接入成功率。

### 5.2 基础数据查询模块实现

基础查询能力由 `api/gtfs.py` 提供，涵盖地区、机构、线路、站点、班次、时刻表、轨迹和统计等内容。其实现方式主要有两类：一类是基于单表或简单联表的列表查询，例如线路列表、站点列表；另一类是围绕具体业务对象进行的细粒度查询，例如线路详情、线路方向、线路站点、班次停靠时刻和线路轨迹。

基础查询模块的重要性在于，它是整个系统的“事实底座”。实时监控、准点率、换乘规划和健康度分析都必须依赖 `routes`、`stops`、`trips` 和 `stop_times` 提供的静态结构。只有基础查询模型稳定，分析功能才不会失去参照系。

### 5.3 实时监控模块实现

#### 5.3.1 数据采集服务

准点率服务 `backend/services/punctuality_service.py` 同时承担实时数据采集任务。该服务根据 `region` 选择不同 fetcher：旧金山使用 `GTFSDataFetcher`，悉尼使用 `TfNSWDataFetcher`，纽约预留 `MTADataFetcher`。服务先尝试拉取真实数据，并记录调用耗时、状态码和异常信息到 `api_call_logs`，若连续重试失败且允许降级，则切换至模拟数据模式。

这一设计体现了较强的工程实用性。因为毕业设计环境下第三方接口并不总是稳定可用，如果系统没有降级方案，就会导致实时页面完全不可演示。通过模拟数据回退，平台即使在外部依赖失效时仍能展示基本交互链路。

#### 5.3.2 实时车辆位置实现

车辆位置采集后被写入 `realtime_vehicle_positions` 表，记录车辆编号、班次、线路、经纬度、速度、朝向、位置时间戳和记录时间戳等信息。前端 `RealtimeMonitor.vue` 会定时调用车辆接口，展示活跃车辆列表、位置摘要和更新时间。若前端开启自动刷新，还可以按 10 秒、30 秒、1 分钟或 5 分钟粒度轮询数据。

实时车辆模块的重点不只是显示经纬度，而是将抽象位置转化为可理解信息。例如页面会结合线路编号、车辆编号、当前站点、速度和最近更新时间展示当前运行状态，使用户能够快速判断车辆是否处于正常移动中。

#### 5.3.3 历史轨迹回放实现

对于位置历史数据，系统提供日期维度查询和轨迹回放功能。该模块可用于观察某辆车在指定日期内的运行路径，对教学演示和问题排查都具有价值。与“实时位置”只反映当前状态不同，历史回放强调对过去运行过程的再现，是连接实时监控和事后分析的重要桥梁。

### 5.4 准点率分析模块实现

#### 5.4.1 准点率计算模型

`business_logic/punctuality_calculator.py` 定义了 `PunctualityThresholds`、`DelayRecord`、`PunctualityRecord`、`RoutePunctualityStats` 和 `SystemPunctualityOverview` 等数据结构，并通过 `PunctualityCalculator` 完成延误记录接收、状态分类、缓存更新和统计聚合。

当系统接收到一条延误记录时，会根据到站延误秒数判断其属于提前、准点、延误还是严重延误，并更新对应线路与站点的计数和平均值。这样，系统既可以执行离线汇总，也可以在内存中逐条累积统计，具有良好的计算直观性。

#### 5.4.2 多粒度统计实现

准点率分析并非只有单一线路排行，而是形成四个层次。

1. 明细层：`realtime_delay_records` 保存逐条延误记录。
2. 聚合层：`route_daily_punctuality` 和 `stop_daily_punctuality` 保存日级统计。
3. 分布层：`hourly_punctuality_stats` 保存小时级统计。
4. 概览层：`system_punctuality_overview` 保存系统总体指标与最佳、最差线路摘要。

这种设计能够在不同页面以最适合的粒度读取数据。例如概览页优先读取系统总览，线路详情页读取线路日统计，小时分布页读取小时粒度聚合，实时监控页则读取最近延误明细。分层统计显著减少了前端重复计算压力。

#### 5.4.3 可配置阈值实现

系统在 `punctuality_config` 表中保存准点率相关阈值和分析参数，例如提前阈值、准点阈值、严重延误阈值、高峰时段开始结束时间和数据保留天数等。与把阈值写死在代码中的做法相比，配置表方式更利于后续调整统计口径，也更符合实际业务场景中“不同城市对准点定义可能不同”的特点。

#### 5.4.4 前端分析页面实现

前端围绕准点率构建了概览、线路准点率、站点准点率、趋势总览、线路详情和站点详情等多个页面。用户既可以查看整体统计，也可以深入到单条线路或单个站点。结合图表与表格，系统能够同时展现排名、趋势和明细。与简单输出单个百分比相比，这种多层次展示更利于理解公交运行状态。

### 5.5 换乘规划模块实现

`transfer_planner.py` 是系统中较有代表性的算法模块之一。其基本思想是：从起点站出发，查询经过当前前沿站点的线路，并为每条线路选择一个代表班次；随后沿班次停靠序列向后扩展，构造可乘坐的区段；若到达终点，则生成换乘方案，否则将新站点纳入下一轮前沿。系统默认允许最多 3 次换乘，并在每轮中通过“每站仅保留累计时间最短路径”的方式压缩状态规模。

该算法并不是严格意义上的最优公共交通路径规划算法，但具有三个优点。第一，实现复杂度低，便于与现有 GTFS 时刻表结构直接结合；第二，能够返回分段结果，包括上车站、下车站、线路名、发到站时间和站数，解释性较好；第三，对于中等规模数据集和教学演示场景，查询开销可控。系统还支持 `min_transfer` 与 `min_time` 两种排序策略，分别偏向少换乘和少耗时。

### 5.6 站点可达性分析模块实现

与换乘规划面向具体起终点不同，可达性分析关注“从某站点出发，在给定时间预算内能够到达哪些站点”。`reachability.py` 以起点站为中心，维护 `dist_seconds` 记录最短可达时间，并通过站点前沿集合迭代扩展。为控制搜索复杂度，系统引入两个重要策略：一是对每轮可扩展的班次进行代表性选择，限制最大班次数量；二是对时间进行归一化和跨午夜处理，避免简单字符串比较造成错误。

最终，系统会返回可达站点列表和分层圈层，例如 15 分钟、30 分钟、45 分钟、60 分钟等可达范围。前端可据此在地图上形成圈层概念或列表排序，从而帮助用户理解某一站点的服务覆盖能力。这一功能对于站点选址评价、通勤便利性分析和教学展示都很有意义。

### 5.7 用户功能模块实现

#### 5.7.1 认证与用户管理

用户认证模块提供注册、登录、登出和当前用户信息获取。若 `users` 表为空，系统会自动创建默认管理员账户 `admin/admin`，便于首次启动后快速进入后台。虽然默认口令方式并不适用于真实生产环境，但对毕业设计演示和初始化调试非常实用。

#### 5.7.2 收藏与订阅

收藏模块支持将线路或站点加入用户收藏夹，并通过联合唯一约束避免重复插入。订阅模块允许用户对某条线路设置准点率阈值，当最新统计低于阈值时，系统可生成告警通知。收藏解决的是“高频访问对象快速触达”的问题，订阅解决的是“持续关注对象自动提醒”的问题，两者共同构成个性化体验基础。

#### 5.7.3 通知与公告

通知模块支持分页查询、未读计数、单条或全部已读操作。管理员可发布系统公告，后端会为所有活跃用户批量生成通知。准点率告警则根据订阅表和最新线路统计自动生成。这样，系统不仅是一个查询工具，也成为一个具备主动触达能力的信息服务平台。

### 5.8 管理后台模块实现

#### 5.8.1 数据库与接口健康监控

`admin.py` 中的 `admin_db_stats()` 会查询 PostgreSQL 各表物理大小、估算行数、数据库总大小和活跃连接数，并设置 15 分钟缓存以降低重复查询开销。`admin_api_health()` 则统计过去 24 小时第三方接口调用总量、平均时延、成功数、错误数和最近错误记录。这些指标有助于管理员识别问题来源，是典型的后台运维能力。

#### 5.8.2 数据时效性与用户管理

管理员可查看各地区 `routes`、`stops`、`trips` 的数量以及最近一次导入日志，用于判断静态数据是否及时更新。用户管理模块则支持列出全部用户并进行创建和状态变更等操作，使系统具备基本管理闭环。

#### 5.8.3 审计日志与数据质量

后台还能查看审计日志列表，并支持按动作、用户名和时间范围筛选。数据质量模块依据专门的检查表记录 GTFS 数据问题、严重级别和修复建议，用于发现数据缺失、字段异常或结构问题。对一个数据驱动系统来说，这类“治理型功能”是提高系统可信度的重要组成部分。

### 5.9 扩展分析模块实现

#### 5.9.1 线路健康度评分

健康度评分模块通过 `route_health_scores` 表保存线路在某一日期下的准点率得分、频率稳定性得分、覆盖度得分、延误分布得分和综合得分。其价值在于，将多个指标压缩为更容易理解的单一评价入口，适合排序展示和横向对比。

#### 5.9.2 异常告警

告警模块围绕 `anomaly_alerts` 表实现活跃告警、历史告警、统计摘要和人工解决等功能。告警类型包括车辆停滞、线路延误、站点拥堵和路段缓慢等。相比单纯展示平均值，告警机制更强调对异常事件的捕捉，是从“统计分析”走向“运行监测”的关键一步。

#### 5.9.3 碳排放分析

碳排放模块基于线路距离和公交与私家车排放因子差异，估算一次或多次公交出行相对于私家车出行节省的碳排放量，并保存到 `user_carbon_records` 表中。前端可进一步展示累计节碳、周/月节碳、树木等价量和排行榜。这一功能将系统从“公交信息平台”拓展到“绿色出行倡导平台”，增强了项目的公共服务内涵。

#### 5.9.4 客流预测与智能推荐

客流预测模块并未引入复杂机器学习模型，而是基于站点在不同日期类型和小时的计划班次数量构建相对客流指数。这种方法虽然简单，但实现成本低、解释性强，适合毕业设计项目。智能推荐模块则结合用户收藏和审计日志中的高频访问线路，优先推荐用户偏好的线路，并在无个性化数据时退化为推荐准点率最高的线路。该设计体现了“规则驱动”的轻量化智能实现思路。

### 5.10 数据导出模块实现

前端 `exportHelper.js` 统一封装了 CSV、Excel 和 PDF 三种格式导出。CSV 导出通过 BOM 头兼容中文 Excel 打开；Excel 导出使用 `xlsx` 自动计算列宽；PDF 导出利用 `jsPDF` 和 `jspdf-autotable` 生成横向表格，并对文本执行 Unicode 转义。这使系统中的线路列表、站点列表、统计表和后台报表可以直接导出，方便汇报和二次分析。

### 5.11 前端界面与交互实现

系统前端并不是简单的静态页面集合，而是围绕业务流程进行交互设计。首页通过卡片聚合核心功能，线路和站点页面提供列表与详情跳转，地图页面提供空间感知，实时监控页面支持自动刷新与筛选，分析页面通过图表展示指标变化，后台页面通过表格和统计卡片支持运维管理。

在视觉实现上，Element Plus 提供统一控件风格，ECharts 提供趋势与分布表达，Leaflet 承担地理空间层。前端还支持中英文切换和明暗主题切换，这说明系统不仅考虑功能实现，也考虑到可用性和展示效果。

### 5.12 审计日志与操作追踪实现

审计模块位于 `backend/core/audit.py`，核心函数 `record_audit_log()` 负责将一次关键操作的动作类型、实体类型、实体 ID、额外元数据、用户 ID、用户名、请求 IP 与 User Agent 写入 `audit_logs` 表。调用方式主要有两类：一是后端接口在关键路径上显式调用，例如登录成功、发布公告、修改用户状态等；二是前端在路由切换后异步调用 `/api/audit/page-view` 接口上报页面访问。这种双路径上报能够形成服务端行为日志与用户浏览行为日志的并集，为后续问题排查和统计分析提供数据基础。

审计日志的查询接口支持按动作类型、用户名、时间范围和实体类型筛选，并结合分页机制控制返回量。前端 `AuditLog.vue` 页面通过表格展示审计记录，支持按列排序和筛选，同时提供了导出功能，便于管理员将日志下载后作进一步分析。

### 5.13 数据导出与报表生成细节

数据导出能力的技术实现集中在前端 `utils/exportHelper.js` 文件，其内部封装了三类导出逻辑。CSV 导出通过构造 UTF-8 BOM 头的字符串并触发浏览器下载，解决了中文在 Excel 中打开出现乱码的问题；Excel 导出使用 `xlsx` 库生成工作簿对象，并根据首行字段长度自动计算列宽，同时支持多工作表输出；PDF 导出使用 `jsPDF` 作为绘图引擎，配合 `jspdf-autotable` 插件生成结构化表格，并对包含中文的字段执行 Unicode 转义，以规避默认字体对中文支持不足的问题。

前端页面通过 `exportData()` 等工具函数调用上述逻辑，调用方只需提供列定义、数据源和文件名即可。为了避免大数据量导出阻塞主线程，关键页面还会在导出前后显示加载态，并对超过一万行的数据结果给出提示，建议用户缩小筛选条件后再导出。

### 5.14 前端国际化与主题切换实现

项目支持简体中文（zh-CN）和英文（en）两种语言。`frontend/src/i18n/` 下的语言文件以嵌套对象方式组织文案，按页面或业务模块划分命名空间。语言切换在全局顶栏完成，切换后 vue-i18n 自动触发所有依赖语言键的组件重渲染，并将选择结果写入 `localStorage` 以在刷新后保留。新增 UI 文本时必须同步更新两种语言文件，以避免出现某种语言下的文案缺失。

主题切换由 `themeStore` 管理，其核心逻辑是在 `<html>` 根元素上添加 `dark` 类名，并由 CSS 变量驱动颜色变化。Element Plus 在项目启动时引入其深色模式样式表，项目内部的自定义组件则通过 CSS 变量保持一致性。这一实现较为轻量，避免了在每个组件内部重复判断主题状态。

### 5.15 数据质量审查模块实现

数据质量审查模块是一个典型的治理型功能，其脚本 `data_quality_checker.py` 集成了约二十条检查规则，覆盖 ERROR、WARNING 和 INFO 三个严重级别。ERROR 级规则用于发现数据错误，例如到站时间晚于出发时间、`trips` 引用了不存在的 `route_id` 或 `service_id`、`shapes` 中相邻点距离异常过大、站点经纬度超出合理范围等；WARNING 级规则识别数据质量隐患，例如线路缺失 `shape`、相邻站间隔过短、日历结束日期早于今日、线路只有单一方向等；INFO 级规则提示可改进的元数据，例如线路未设置颜色、站点缺失无障碍信息、班次未关联 `block_id` 等。

检查结果以 `data_quality_checks` 和 `data_quality_issues` 两张表保存：前者记录每次检查的整体汇总，包括错误数、警告数、提示数、综合质量分和检查耗时；后者记录具体问题，包含规则编号、实体类型、实体 ID、中文描述、修复建议和若干示例数据。综合质量分按简化规则计算——ERROR 每个扣 5 分，WARNING 每个扣 1 分，初始分数为 100，最低截断为 0。前端 `DataQualityDashboard.vue` 以仪表盘形式展示当前得分，同时提供按严重级别分页浏览问题列表、查看示例数据和修复建议、以及导出 CSV 报告的能力。

### 5.16 订阅告警与通知投递实现

订阅告警机制将用户感兴趣的线路与其准点率阈值绑定。具体实现为：用户在线路详情页填写阈值并保存后，系统在 `user_subscriptions` 表中插入一条包含 `user_id`、`route_id`、`region` 和 `threshold` 的记录；当新一轮准点率统计写入 `route_daily_punctuality` 后，后端定时任务扫描订阅表，对每条订阅调取线路最新准点率，若低于阈值则在 `notifications` 表中为对应用户生成一条通知，并将类型标记为 `punctuality_alert`。通知同时携带触发线路、阈值、实际值和触发时间等元数据，以供前端组装友好文案。

前端 `NotificationBell.vue` 组件在每次页面渲染时向后端轮询未读通知数，未读数大于 0 时在铃铛图标上显示红色徽章；点击后展示最近通知列表，用户可逐条或全部标记为已读；管理员发布的系统公告也通过同一通道推送，但类型标记为 `announcement`，并在列表中以不同图标区分。该设计用最小的实现成本构建了一套覆盖订阅告警、系统公告和审计提示的统一通知通道。

### 5.17 智能推荐模块实现

智能推荐模块 `api/analysis.py` 中的 `/api/recommendations` 接口采用“规则融合 + 隐式反馈”的轻量方案。推荐分数计算流程为：第一步，从 `audit_logs` 表中查询当前用户近 30 天内访问频率最高的前 20 条线路，统计访问次数作为基础频次；第二步，从 `user_favorites` 表中获取当前用户的收藏线路，将收藏线路的频次乘以 2 作为权重加成；第三步，对候选线路查询 `route_daily_punctuality` 中最新的准点率得分，作为服务质量权重；第四步，综合访问频次、收藏权重和准点率得分计算最终推荐分数，并按分数倒序返回前 `limit` 条结果。

当用户没有足够的行为数据时，系统会退化为推荐当前地区准点率最高的线路，避免首次登录用户看到空页面。推荐结果同时携带“推荐理由”文案，例如“这是您本月访问最多的线路”“最近 7 天准点率达 92%”，以增强推荐的可解释性。前端 `Recommendations.vue` 以卡片形式展示推荐线路，并支持一键收藏或订阅。

### 5.18 车辆历史回放实现

车辆历史回放功能由 `backend/scripts/generate_vehicle_history.py` 与 `frontend/src/views/VehiclePlayback.vue` 共同实现。数据层面，脚本基于 `realtime_vehicle_positions` 表的历史记录，按日期和线路生成可回放的轨迹样本；若当天没有真实采集数据，脚本会根据 GTFS 时刻表模拟车辆运行轨迹，使 `--trips-per-hour` 参数控制的密度下生成符合计划时刻表的虚拟车辆点。这一兼容策略使得回放功能不依赖完整的历史数据积累。

前端 `VehiclePlayback.vue` 使用 Leaflet 在地图上绘制轨迹线，并通过时间滑块控制播放进度。用户可调节播放速度、暂停、单步前进或后退，还可选择不同线路同时对比。地图标记的颜色和图标根据车辆状态（运行中、停靠、异常）动态切换。该功能不仅提供视觉上的“历史重现”能力，也为教学演示提供了直观示例，方便讲解 GTFS-Realtime 数据如何构成完整的运行轨迹。

本章围绕系统核心模块，详细介绍了静态数据导入、基础查询、实时监控、准点率分析、换乘规划、可达性分析、用户功能、管理后台、扩展分析、数据导出和前端交互等实现内容。可以看到，项目已经形成较完整的业务闭环：数据从 GTFS/GTFS-Realtime 接入，经过数据库组织与业务计算后，以列表、图表、地图和通知等方式面向用户和管理员呈现。下一章将进一步抽取其中具有代表性的算法与数据处理机制进行分析。

## 第6章 关键算法与数据处理机制

### 6.1 多地区数据隔离机制

#### 6.1.1 设计动机

若系统只服务单一城市，最简单的做法是为每个数据集单独建立数据库或在表中仅保存单地区数据。但本项目需要在统一平台内支持多个地区，同时保证前端交互和接口路径尽可能一致。如果采用“每个地区一套完全独立表”的方式，会导致代码重复和运维复杂；如果完全不区分地区，则会在 `route_id`、`stop_id` 等主键上产生冲突。

因此，系统选择在核心表中引入 `region` 字段，并将其纳入主键或联合唯一约束。这一方案具有以下特点。

1. 结构统一。所有地区共享一套表结构和接口。
2. 逻辑隔离。不同地区的数据通过 `region` 显式区分。
3. 查询明确。所有核心接口都可通过 `region` 参数切换上下文。
4. 扩展方便。新增地区时，主要新增数据源配置与导入数据，不需要复制整套代码。

#### 6.1.2 关键实现方式

在数据库层，`routes`、`stops`、`trips`、`stop_times` 等表以 `(region, id)` 形式作为主键；在导入层，导入器为每条记录附加 `region`；在清理层，删除操作始终限制在指定地区范围；在接口层，大多数 SQL 条件都会明确写出 `WHERE region = %s`；在前端层，地区选择器可以将所选地区透传给 API 模块。这构成了较完整的多地区隔离闭环。

从软件工程角度看，该机制是一种轻量级多租户思想在交通数据系统中的具体应用。它避免了过重的租户中间件，也避免了完全独立部署的管理负担，适合课程项目和中小规模平台。

### 6.2 GTFS 依赖感知导入机制

GTFS 数据导入的关键难点并不在文件读取，而在关系依赖处理。以 `stop_times` 为例，它依赖 `trips` 和 `stops` 两张表；`trips` 又依赖 `routes`；`routes` 可能依赖 `agency`。如果导入顺序任意，就会触发外键错误。因此，导入器以 `TABLE_ORDER` 明确规定导入顺序，并按该顺序遍历文件。

导入器还采用两项关键策略。

第一，基于数据库实际列的字段匹配策略。导入前先查询目标表列名，只对匹配列插入数据，忽略未知列。这样即使源数据包含本系统暂未建模的扩展字段，也不会破坏导入流程。

第二，批量写入策略。导入器使用 `execute_batch` 执行分页批量插入，从而降低逐行插入带来的事务开销。对于包含大量 `stop_times` 记录的 GTFS 数据集，这一点尤其重要。

该导入机制说明，标准数据接入并不是简单文件复制，而是需要结合数据库约束、性能需求和异构兼容性进行整体设计。

### 6.3 准点率分类与聚合算法

#### 6.3.1 延误状态分类

系统将每条延误记录抽象为 `DelayRecord` 对象，包含 `trip_id`、`route_id`、`stop_id`、`scheduled_time`、`actual_time`、`arrival_delay` 和 `departure_delay` 等字段。核心分类函数 `_get_punctuality_status()` 依据阈值将其划分为四类。

```text
delay < -E                    => EARLY
|delay| <= O                  => ON_TIME
O < delay <= V                => LATE
delay > V                     => VERY_LATE          （6-1）
```

式中，`E` 为提前阈值，`O` 为准点阈值，`V` 为严重延误阈值。默认情况下 `E=60` 秒，`O=120` 秒，`V=300` 秒。

这种分类方法兼顾了实际公交运行中“少量秒级偏差可视为正常”的现实特征，避免把所有偏差都当作异常，从而提高评价结果的业务可解释性。

#### 6.3.2 在线缓存更新

当新延误记录加入后，系统不仅存储原始数据，还同步更新内存中的 `punctuality_cache`。缓存键由 `route_id` 与 `stop_id` 组合构成，对应 `PunctualityRecord`。其更新内容包括：

1. 总样本数加一；
2. 按分类增加准点、提前、延误或严重延误计数；
3. 更新平均到站延误和平均离站延误；
4. 更新最大延误和最小延误；
5. 修正统计时间范围。

这一机制使系统能够在实时采集过程中维持局部统计状态，而不必每次都对全量历史记录重新聚合。虽然当前系统最终仍会将结果写入数据库做离线聚合，但在线缓存有助于降低短期统计的计算成本。

#### 6.3.3 多粒度聚合

系统将准点率聚合拆分为线路、站点、小时和系统四类，其中各指标之间并非独立关系，而是由同一批原始延误记录派生而来。若用 `D_r` 表示某线路在统计期内的延误记录集合，则有：

```text
P_r = |{d ∈ D_r | status(d)=ON_TIME}| / |D_r| × 100%     （6-2）
```

站点准点率 `P_s` 与之类似，只是统计对象从线路变为站点。系统总体准点率则可看作所有线路记录的全局汇总：

```text
P_sys = N_on_sys / N_total_sys × 100%                    （6-3）
```

小时粒度统计进一步引入 `hour_of_day` 维度，使系统能够观察高峰期和非高峰期的差异。对于公交运营来说，这种分层聚合比单一平均值更能揭示问题，因为某条线路可能整体均值尚可，但在早高峰明显恶化。

### 6.4 换乘规划算法分析

#### 6.4.1 算法思想

项目中的换乘规划算法可以概括为“基于站点前沿的分层展开”。其步骤如下。

1. 从起点站出发，构建初始前沿 `frontier={from_stop}`。
2. 查询当前前沿站点经过的线路及其代表班次。
3. 沿代表班次的后续站点序列扩展可到达站点，形成新的路径片段。
4. 若新站点为目标站，则保存方案；否则进入下一轮换乘扩展。
5. 每轮只保留每个站点累计时间最短的路径，限制状态数量。
6. 达到最大换乘数后停止。

这一策略与传统图搜索算法的最大区别在于，它并未把所有停靠事件完全展开，而是通过“每条线路每个变体只取一个代表班次”显著压缩状态规模。该方法牺牲了一部分严格最优性，但换来了更低的实现复杂度和更强的可读性。

#### 6.4.2 复杂度控制策略

若不加约束地枚举所有可乘坐班次，状态数量会迅速增长。项目中主要采用三种控制策略。

1. 限制最大换乘次数 `MAX_TRANSFERS=3`。
2. 对于同一站点的同一路线同一 headsign，仅保留一个代表班次。
3. 对新前沿中的每个站点只保留累计时间最短路径。

这些约束使算法在公交中等规模数据集上具备较好的交互可行性。对毕业设计而言，这种方法比引入复杂预处理算法更符合“可实现、可解释、可演示”的要求。

#### 6.4.3 与经典算法的关系

从研究视角看，本项目算法与 RAPTOR[11] 在思想上存在一定相似性，即都强调按线路而不是按图上全部节点进行搜索，并将换乘次数作为天然轮次。但项目实现远比 RAPTOR 简化，不处理完整的 Pareto 最优解集，也没有进行更复杂的时刻表动态更新支持。正因如此，本文将其定位为“受公共交通特化搜索思想启发的轻量实现”，而不是严格复现成熟研究算法。

### 6.5 站点可达性扩展算法分析

站点可达性分析在本质上是一个带时间预算约束的多源可达问题。项目实现中，`dist_seconds` 保存从起点站到每个站点的当前最短耗时，`frontier` 保存当前轮需要向外扩展的站点集合。对于前沿中的每个站点，系统查询可上车班次，再沿班次序列计算到后续站点的旅行时间和候车时间之和。

若设起点站为 `s_0`，目标站点为 `s_i`，则其候选耗时可表示为：

```text
cost(s_i) = cost(board_stop) + wait_time + travel_time     （6-4）
```

其中 `wait_time` 由默认上车等待时间与时刻归一化共同决定，`travel_time` 由班次中上下车时刻差得到。当 `cost(s_i)` 小于当前记录且未超过最大时间预算时，更新 `dist_seconds[s_i]`。

项目还构建了“圈层”概念，即将到达时间映射到 15 分钟、30 分钟、45 分钟、60 分钟等分层限制下。这样不仅能返回一个简单列表，还能形成“此站点 30 分钟生活圈”的空间表达，增强可视化价值。

### 6.6 线路健康度评分算法

健康度评分脚本 `calculate_health_scores.py` 采用多指标加权综合方式，对每条线路在某日的运行状况进行评价。其核心包含四个维度。

1. 准点率得分 `C_p`，权重 40%；
2. 频率稳定性得分 `C_f`，权重 25%；
3. 覆盖度得分 `C_c`，权重 15%；
4. 延误分布得分 `C_d`，权重 20%。

综合得分计算公式为：

```text
C_total = 0.40×C_p + 0.25×C_f + 0.15×C_c + 0.20×C_d     （6-5）
```

其中，准点率得分直接取近 7 日平均准点率并截断到 100；频率稳定性通过首站发车间隔标准差 `σ` 计算：

```text
C_f = clip(100 - 1.67×σ, 0, 100)                        （6-6）
```

标准差越小说明发车间隔越稳定，得分越高。覆盖度得分则综合线路站点数与方向数相对地区平均值的比率；延误分布得分通过“轻度延误占比高则加分、严重延误占比高则减分”的思路构建：

```text
C_d = clip(light_pct - 0.5×severe_pct, 0, 100)         （6-7）
```

这一评分模型并不等价于交通行业中的正式考核标准，但它把多个维度统一到同一尺度上，有利于进行排序展示与历史趋势观察。

### 6.7 异常告警生成机制

告警服务 `alert_service.py` 通过对实时车辆、线路准点率和客流热力图数据进行规则扫描，生成若干类型的告警。其规则主要包括：

1. 车辆滞留告警：同一车辆在较长时间跨度内保持多次位置样本，可判断为疑似长时间停滞。
2. 线路低准点率告警：最新统计日期下，准点率最低且平均延误较高的线路生成 `route_delay` 或 `segment_slow` 告警。
3. 站点拥挤告警：客流指数最高的站点生成 `stop_congestion` 告警。

其中，线路告警严重程度由准点率与平均延误共同决定。例如准点率低于 60% 或平均延误超过 420 秒可判为 `critical`，低于 70% 或超过 300 秒判为 `high`。这是一种典型的规则驱动异常检测方案，优点是实现简单、阈值明确、便于人工理解和调整。

### 6.8 碳排放计算机制

碳排放服务 `carbon_service.py` 首先计算线路里程，优先使用缓存表 `route_distances`，若无缓存则尝试根据 `shape` 点序列使用地理距离公式计算；若仍无可用轨迹，则退化为基于站点数量估算线路长度。然后根据 `route_type` 选择公交排放因子，与私家车排放因子 `CAR_EMISSION=0.271` 进行比较，得到公交排放、私家车排放和节省量。

若设单次行程距离为 `L`，公交排放因子为 `e_t`，私家车排放因子为 `e_c`，则：

```text
E_transit = L × e_t                                     （6-8）
E_car     = L × e_c                                     （6-9）
E_save    = E_car - E_transit                           （6-10）
```

用户若一次录入多次乘坐，则系统按乘坐次数 `n` 对距离和排放量线性放大。这一模型虽然较为简化，但足以反映公共交通相较私家车在碳减排方面的方向性优势。

### 6.9 客流预测与推荐机制

客流预测服务采用“班次密度近似客流强度”的思路。具体而言，系统统计指定站点在工作日或周末各小时的计划发车班次数，并计算相对于该站点平均班次的比例，作为客流指数：

```text
FlowIndex_h = trips_h / avg(trips_0...23) × 100         （6-11）
```

这一方法并不直接等价于真实客流人数，但在缺少刷卡数据、视频计数数据或手机信令数据的情况下，能够提供一种廉价且可解释的客流近似度量。对教学和原型系统而言，这种方式具有较高性价比。

推荐机制则采用规则融合方式：优先从用户收藏线路和近 30 天审计日志中提取候选线路，再结合线路准点率赋分；若没有个性化数据，则推荐最新统计中准点率最高的线路。虽然未使用协同过滤或深度学习模型，但已体现“用户偏好 + 服务质量”的组合思路。

### 6.10 数据库索引与查询优化策略

在 GTFS 系统中，查询性能是影响用户体验的重要因素。由于 `stop_times` 等表在导入旧金山完整数据集后可能达到百万量级，若未建立合适的索引，按线路或站点过滤延误记录时极易触发全表扫描。为此，本项目在设计阶段针对高频查询字段建立了多组索引。

第一组索引围绕 `realtime_delay_records` 表展开，分别在 `(region, route_id)`、`(region, stop_id)` 和 `(region, record_time)` 上建立普通索引，覆盖线路维度、站点维度和时间维度的过滤查询。此外，在 `(region, route_id, record_time)` 上建立复合索引，用于支持“某线路最近 N 条延误记录”这类组合查询。

第二组索引围绕 `route_daily_punctuality` 和 `stop_daily_punctuality` 聚合表，以 `(region, stat_date)` 为索引键，用于支持按日期快速拉取全线路排行。第三组索引围绕 `realtime_vehicle_positions` 表，以 `(region, vehicle_id, position_timestamp)` 为索引键，支持车辆历史轨迹回放查询。

除索引外，系统还引入若干查询优化策略。对于后台仪表盘中的数据库容量统计查询，使用 15 分钟内存缓存避免频繁扫描系统表；对于线路健康度历史趋势查询，通过在 `route_health_scores` 表上建立日期索引，使趋势折线图能够在秒级返回；对于站点可达性计算这类复杂度较高的查询，采用“按站点预取发车班次列表，在内存中裁剪代表班次”的方式，将数据库交互次数控制在可接受范围。

### 6.11 前端路由守卫与权限控制实现

前端路由守卫是系统安全的重要组成部分。`router/index.js` 中的 `beforeEach` 钩子在每次导航前检查三类信息：当前路由是否允许未登录访问（如登录页）、当前是否存在有效 `auth_token`、当前路由是否需要管理员权限。若未登录访问受保护页面，则重定向到登录页并记住目标路径，登录成功后自动跳转回原页面；若普通用户访问管理员页面，则给出提示并返回首页。

`afterEach` 钩子则在页面渲染后异步调用 `/api/audit/page-view` 接口，将访问记录写入审计日志。为了避免审计请求失败影响页面显示，该调用以 `try/catch` 包裹并忽略错误。前后端分离场景下，这种“前端负责触发、后端负责落库”的审计模式，既保持了用户感知的流畅，也保证了操作追踪的完整性。

### 6.12 配置加载优先级与地区参数传递

配置加载采用“环境变量 > `config.local.json` > `config.json`”的优先级策略，实现方式在 `core/config.py` 中。系统启动时，首先读取 `config.json` 作为默认配置，再用 `config.local.json` 覆盖其中本地化字段，最后读取指定环境变量覆盖敏感字段（如 API Key）。这种分层覆盖方式既满足了团队共享默认配置的需求，又支持不同开发者在本地保留个性化设置，还能通过环境变量注入生产密钥，兼顾了便捷性与安全性。

地区参数的传递则分布在多个层次。前端 `regionStore` 维护当前选中地区，并将其写入 `localStorage` 以便刷新后保持；Axios 请求拦截器在每次发送请求时自动附加 `region` 查询参数；后端 `get_region()` 辅助函数从 query string 或请求体中读取参数，默认为 `sf`；各数据库查询在 WHERE 子句中显式写出 `region = %s` 条件。这种“前端自动注入 + 后端一致过滤”的模式，使业务开发者无需关心多地区隔离的具体实现细节。

### 6.13 实时数据获取的重试与降级策略

`PunctualityDataService` 在采集实时数据时引入了多层重试与降级机制。第一层是 HTTP 请求级别的重试：对单次 API 调用，系统在捕获超时或 5xx 错误后，以指数退避方式最多重试三次；每次请求都会记录耗时、状态码和错误信息到 `api_call_logs` 表，为后续接口健康统计提供数据。第二层是服务级别的降级：若连续多次重试仍然失败，且当前配置允许降级，系统将切换至 `MockDataGenerator` 生成的模拟数据模式，保证实时监控页面仍可展示基本交互。

模拟数据生成器基于 GTFS 静态数据构造符合时刻表的虚拟车辆位置和延误记录，并在延误值上引入随机扰动以模拟真实运行波动。这种设计的价值不仅体现在外部接口不稳定时保持演示可用，也体现在开发阶段不具备 API Key 或本地无法访问外部网络时仍可完成端到端联调。

### 6.14 跨午夜时间处理与 GTFS 时刻规范

GTFS 规范允许 `stop_times` 中的时间值超过 24 小时，以便表达跨午夜班次。例如，一列在午夜 0 点 30 分发车的班次如果属于前一运营日，应该以 `24:30:00` 而不是 `00:30:00` 表示。这一规定使得系统在时间比较时不能直接将字符串作为普通时间解析，否则会出现“晚于 24:00:00 的班次排在 00:00:00 之前”的逻辑错误。

为此，项目在换乘规划和可达性分析中引入了统一的时间归一化函数 `parse_gtfs_time()`，将字符串拆分为时、分、秒后累加为秒级整数，并在需要比较时直接使用整数进行判断。该函数既兼容常规 `HH:MM:SS` 格式，也正确处理 `HH` 大于等于 24 的情况。对于跨运营日的候车时间，系统进一步引入 `wait_time` 上限约束，避免出现不合理的长等待方案。这些细节对保证查询结果正确性至关重要。

### 6.15 本章小结

本章从多地区隔离、依赖感知导入、准点率聚合、换乘规划、可达性扩展、线路健康度、异常告警、碳排放和客流预测等角度，对系统中的关键算法与数据处理机制进行了分析。可以看出，项目在算法上并未一味追求复杂模型，而是围绕毕业设计场景与工程可行性，选择了规则明确、实现成本可控、结果可解释的方案。这种设计使平台既具备分析深度，也保持了较高的可维护性。

### 7.4 脚本化测试设计与结果分析

#### 7.4.1 API 快速测试

`backend/tests/test_api_quick.py` 对以下高频接口进行 smoke test：健康检查、统计概览、实时汇总、准点率概览、线路准点率、站点准点率、小时统计、配置查询、线路查询和站点查询。该脚本通过 `requests` 逐个访问接口，并根据统一 JSON 返回结构判断是否成功。其意义在于，在系统启动后能够快速确认基础链路是否正常。

从测试设计看，这种脚本虽然没有覆盖全部接口，但覆盖了系统最具代表性的查询入口。如果这些核心接口全部返回正常，说明数据库连接、Blueprint 注册、基本查询逻辑和统一响应格式大体可用。

#### 7.4.2 准点率逻辑测试

`backend/tests/test_punctuality.py` 直接构造多条 `DelayRecord` 样本，验证准点率计算器对提前、准点、严重延误等场景的分类能力，并检查系统概览、线路统计和延误汇总输出。这种“先脱离真实接口构造样本，再观察算法输出”的方法适合验证业务计算逻辑，能够避免把所有问题都归因于外部数据源。

#### 7.4.3 数据库与数据明细检查

`check_db.py` 和 `check_data_detail.py` 用于检查数据库结构与导入数据细节。对于 GTFS 系统而言，很多问题并不会表现为接口报错，而可能是某张表为空、主外键关系不完整或某地区数据未正确导入。因此，数据库检查脚本是非常必要的。

#### 7.4.4 新功能回归测试

`test_new_features.py` 用于验证新增分析模块和扩展功能。尽管项目未建立标准化 CI 流水线，但这种分模块脚本方式已经具备基本的回归测试意识，即在新增功能后对已有能力进行复核。

### 7.5 典型业务流程验证

#### 7.5.1 乘客查询与分析流程

典型流程一为普通用户登录后查看首页，从首页进入线路列表，再进入某条线路详情与准点率分析页，随后对线路进行收藏或订阅。该流程验证了认证、静态查询、分析页面、用户行为和通知服务之间的联动关系。

#### 7.5.2 实时监控流程

典型流程二为进入实时监控页面，观察活跃车辆数量、最近延误、延误线路和车辆位置列表，并根据自动刷新开关持续观察数据变化。该流程验证了实时数据采集、实时表读取、前端定时刷新和筛选交互的完整性。

#### 7.5.3 出行辅助流程

典型流程三为在换乘规划页面输入起点和终点站，获取候选换乘方案；在可达性分析页面输入起点站和时间限制，查看可达站点范围；在路线对比页查看不同线路综合差异。该流程验证了分析工具的业务实用性。

#### 7.5.4 管理后台流程

典型流程四为管理员登录后访问后台，查看数据库统计、API 健康、数据时效性、审计日志和用户管理页面，并尝试发布公告或触发健康度重算。该流程验证了权限边界和后台治理功能的完备程度。

### 7.6 非功能测试与分析

#### 7.6.1 可维护性分析

从代码结构看，后端目录分为 `api`、`business_logic`、`data_acquisition`、`services`、`scripts`、`core` 和 `database` 等子目录，职责划分清晰；前端按 `views`、`components`、`stores`、`api` 和 `router` 拆分，便于迭代。对于毕业设计项目，这是比较理想的组织方式。

#### 7.6.2 可扩展性分析

系统已支持旧金山湾区、纽约地铁和悉尼三个地区，且通过 `region` + fetcher 映射实现数据切换。这表明架构层面对新增地区具备一定扩展基础。数据库扩展表由独立 SQL 文件维护，也说明新增业务模块时不必改动主 schema。

#### 7.6.3 容错性分析

准点率服务支持重试和模拟数据降级，后台统计使用缓存减少数据库压力，错误响应统一封装，这些都体现了系统具备基础容错意识。尤其是模拟数据回退机制，使平台在演示或外部接口故障时仍可维持主要功能。

#### 7.6.4 安全性分析

系统已实现密码哈希、登录鉴权、管理员权限校验和审计日志记录，具备基本安全能力。但也存在若干不足，例如 token 仅存于内存、缺少过期机制、缺乏更严格的接口限流与细粒度权限策略。这些不足并不影响毕业设计原型的完整性，但应在后续工作中完善。

### 7.7 存在的问题与改进方向

尽管系统已经覆盖大量功能，但通过分析仍可发现一些不足。

1. 路径规划算法较为轻量，尚未达到成熟公共交通规划算法的精度与效率水平。
2. 客流预测和推荐模块以规则为主，缺乏更丰富的历史行为和机器学习建模支撑。
3. 认证机制适合开发环境，但不适合大规模生产部署。
4. 自动化测试仍以脚本为主，缺乏统一测试框架、覆盖率统计和持续集成流程。
5. 前端虽支持国际化与主题切换，但在移动端适配和极端数据量场景下仍有进一步优化空间。

这些问题说明，本系统虽然已经形成完整原型，但仍具备显著的后续研究与工程优化空间。

### 7.8 数据规模与性能观察

在旧金山湾区完整 GTFS 数据集导入后，`routes` 表约包含数百条线路记录，`stops` 表约包含数千条站点记录，`trips` 表达到数万量级，而 `stop_times` 表通常超过百万行。基于这一数据规模，系统在常规查询中表现出如下性能特征：线路列表查询在百毫秒内返回，站点详情页的时刻表查询通过索引可在 200 毫秒内完成，准点率概览查询在聚合表的支撑下通常在 500 毫秒内返回。

换乘规划接口在默认最大换乘 3 次、每个线路仅保留一个代表班次的约束下，一次查询的平均响应时间在 1 至 3 秒之间。若用户请求较偏远站点之间的换乘路径，由于可达线路数量增加，搜索时间可能延长至 5 秒左右。为提升体验，前端在调用该接口时显示加载态进度条并允许取消。站点可达性分析由于涉及多轮前沿扩展，默认 60 分钟时间预算下一次查询耗时约 2 至 4 秒；若时间预算放宽至 90 分钟，覆盖站点数显著增长，查询耗时也会上升至 6 秒左右。

实时数据采集的典型耗时取决于第三方接口。旧金山 511 API 在网络正常情况下单次车辆位置拉取约 1 至 2 秒，悉尼 TfNSW API 略慢，约 2 至 4 秒；纽约 MTA Protocol Buffers 接口由于消息体积较小反而更快，约 0.5 至 1 秒。系统以 30 秒至 1 分钟的间隔循环采集，既能保持数据新鲜度，又不会对第三方服务造成压力。

### 7.9 关键场景压力测试与边界情况

为进一步检验系统稳定性，本文针对若干关键场景进行了简化压力测试。第一类是高并发查询场景：使用 Python 脚本以 10 个并发线程同时调用准点率概览接口，连续运行 60 秒后统计成功率、平均响应时间和 95 分位响应时间。测试结果表明，系统在持续压力下响应稳定，未出现接口超时或数据库连接耗尽。

第二类是大数据量导入场景：使用完整旧金山湾区 GTFS 数据集（包含超过百万条 `stop_times` 记录）测试导入流程。结果显示，在开启批量插入和事务提交策略的情况下，整体导入耗时约 3 至 5 分钟，符合预期。导入过程中没有出现外键约束错误，表明 `TABLE_ORDER` 顺序设计与“按数据库实际列匹配 CSV 字段”的兼容策略可靠。

第三类是边界输入场景：包括查询不存在的 `route_id`、请求超大分页（如 `limit=10000`）、在实时监控页面切换到无数据的地区、在换乘规划中填入同一站点作为起终点等。系统对这些情况均给出了合理的错误提示或空结果，没有出现未捕获异常，说明后端参数校验和前端防御式编程整体到位。

### 7.10 与典型公交 APP 的对比分析

为评价系统实现在功能覆盖上的完整性，本节将其与几类典型公交信息应用进行横向对比。与面向公众的商业地图类应用（如 Google Maps 公交模式）相比，本系统在算法精度、实时性和空间覆盖上存在差距，例如没有实现路口级步行导航和拥堵路况建模；但在分析深度、指标可配置性和后台治理能力上更具特色，例如支持准点率阈值调整、健康度评分和数据质量审查等。这使得本系统更接近面向运营管理或研究分析场景的平台工具，而不是面向终端乘客的导航应用。

与开源社区中的 GTFS 浏览工具（如 Transitland、MobilityData 相关项目）相比，本系统在数据可视化、地区切换、多维度分析和用户交互上更加完整，并且完整实现了前后端闭环；但在数据规模处理、标准兼容度和验证器规则覆盖上弱于这些专用工具。综合来看，本系统在“功能覆盖广度”和“工程完整度”之间取得了较为平衡的位置，适合作为毕业设计展示综合能力，也具备进一步扩展的基础。

本章从测试目标、测试方法、静态结构核查、脚本化测试、典型业务流程验证和非功能分析等方面对系统进行了较系统的评估。结果表明，平台在功能覆盖、模块组织、扩展能力和工程完整性方面表现较好，能够支撑毕业设计所要求的完整实现。同时，测试也揭示了算法复杂度、认证机制和自动化测试体系等方面的改进空间，为后续完善提供了方向。

## 结论

本文围绕“基于 GTFS 的公交智能分析平台设计与实现”这一主题，结合实际项目完成了从需求分析、总体设计到详细实现和测试分析的完整论述。研究结果表明，以 GTFS 和 GTFS-Realtime 为数据基础，结合 Flask、Vue 3 和 PostgreSQL 等通用 Web 技术，可以较为高效地构建一个面向公交场景的综合信息平台，并在同一系统内实现静态查询、实时监控、准点率分析、换乘辅助、个性化服务和后台治理等多种能力。

本文的主要工作和结论可概括如下。

第一，完成了一个面向多地区数据源的公交信息平台原型设计。系统通过在核心表中引入 `region` 字段，实现了多地区数据隔离与统一接口访问，证明了基于标准化数据模型构建跨地区公交平台的可行性。

第二，围绕公交运行评价构建了较完整的准点率分析链路。系统能够从 GTFS-Realtime 数据中提取延误信息，并形成线路、站点、小时和系统级多粒度统计结果，说明基于标准动态数据的运行分析具有较强实践价值。

第三，完成了多项面向用户体验和管理治理的扩展功能，包括换乘规划、站点可达性分析、收藏订阅、通知中心、数据质量看板、线路健康度评分、异常告警、碳排放统计和客流预测等。这些功能表明，公交信息平台不应只停留于线路查询，而应发展为面向用户、运营和管理三方的综合服务系统。

第四，项目在工程实现层面具备较好的结构化特征。后端采用 Blueprint 模块化组织，前端采用路由、状态和组件分层，数据库按主数据与扩展能力拆分 schema，辅以启动脚本、测试脚本、配置管理和审计日志等机制，使系统具备较好的可维护性和演化基础。

当然，本文也存在不足。路径规划算法仍较轻量，未采用更高性能的专业公共交通搜索框架；客流预测和推荐策略以规则为主，智能化程度有限；认证和测试机制仍偏向原型系统；尚缺少面向大规模真实运行环境的性能压测与部署验证。这些不足意味着，本文工作更适合被视为一个“结构完整、功能丰富、可持续扩展的公交智能分析平台原型”。

从开发过程总结看，本文在设计与实现阶段也积累了若干经验。第一，数据标准优先的思想在跨地区数据整合中发挥了关键作用，使得增加新地区的工作量显著低于重新实现；第二，保持算法的规则可解释性比追求精度更重要，因为可解释的结果更容易被使用者接受并在必要时进行人工修正；第三，将耗时操作封装为独立脚本而不是嵌入 HTTP 请求，有助于在不增加架构复杂度的前提下避免响应阻塞；第四，前端状态管理与路由守卫的集中化，使得新增功能时只需少量改动即可继承既有的认证、审计和国际化能力。

总体而言，本文完成的系统已经能够较好体现毕业设计在“问题分析、标准理解、系统设计、代码实现和工程验证”五个方面的综合要求。未来可以进一步从以下方向深化研究：一是引入更成熟的公交路径规划算法（如 RAPTOR 或 CSA）和更精细的换乘约束，使路径结果在大规模网络中仍保持较好的计算效率；二是结合真实历史运行数据引入机器学习模型，提升客流预测、异常检测和推荐的精度与鲁棒性；三是将认证、测试和部署体系升级为更接近生产环境的方案，例如引入 JWT 令牌、统一测试框架和容器化部署；四是继续丰富可视化交互和移动端体验，使平台既能在桌面端支持复杂分析，也能在移动端为外出乘客提供便捷服务；五是探索多模态数据融合，将 GTFS 与气象、活动、节假日等外部数据结合，构建更具前瞻性的预测与调度能力。可以预期，随着更多真实公交数据和更完善工程设施的加入，该平台具备向更高质量智慧交通应用演进的潜力。
