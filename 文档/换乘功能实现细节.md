# 换乘功能实现细节

## 1. 功能概述

用户选择起点站和终点站后，系统基于 GTFS 静态数据（stops、stop_times、trips、routes）搜索候选换乘方案，支持"最少换乘"和"最短时间"两种排序策略，最多支持 3 次换乘。

## 4. 后端算法详解

### 4.1 整体架构

```
find_transfer_plans(from_stop_id, to_stop_id, region, strategy)
│
├── 验证起终点站存在
│
└── 分层 BFS（最多 4 层：第 0 层=直达，第 1~3 层=1~3 次换乘）
    │
    ├── SQL 1: _get_routes_through_stops(frontier_ids)
    │   → 查 frontier 各站经过的线路，每条线路每个变体取 1 个代表 trip
    │
    ├── SQL 2: _get_stops_for_trips(trip_ids)
    │   → 查代表 trip 的完整站点序列
    │
    ├── Python 内存遍历：对每个 frontier 站点的每条线路的下游站点
    │   ├── 命中终点 → 记录方案
    │   └── 未命中 → 加入 new_frontier
    │
    ├── 找到方案 → 终止搜索
    └── 未找到 → frontier = new_frontier，进入下一层
```

### 4.2 关键设计决策

#### 为什么用"代表 trip"而不是全量 trip？

SF 地区有 60,488 个 trip 和 231 万条 stop_times。如果对每个 frontier 站点查询所有经过的 trip，再查每个 trip 的站点序列，数据量会爆炸。

**核心观察**：同一条线路同一变体（trip_headsign）的不同 trip，站点序列是相同的（只是发车时间不同）。因此只需取 1 个代表 trip 就能确定该线路变体能到达哪些站点。

```sql
SELECT DISTINCT ON (st.stop_id, t.route_id, COALESCE(t.trip_headsign, ''))
    ...
FROM stop_times st
JOIN trips t ...
ORDER BY st.stop_id, t.route_id, COALESCE(t.trip_headsign, ''), st.departure_time
```

这将需要处理的 trip 数从数万压缩到每站几个（每条线路每个变体 1 个）。

#### 为什么按 trip_headsign 而不是 direction_id 分组？

GTFS 数据中，同一 `direction_id` 下可能存在不同的分支变体。例如 SF 线路 6：
- direction_id=1, headsign="Downtown Berkeley"：经过站点 A 集合
- direction_id=1, headsign="Civic Center Station"：经过站点 B 集合

A 和 B 完全不重叠。如果只按 direction_id 取代表 trip，会遗漏整个分支。

#### frontier 剪枝策略

每层搜索结束后，对 new_frontier 做剪枝：
- 每个站点只保留累计时间最短的 1 条路径
- 已访问过的站点不再重复展开

这将 frontier 规模控制在合理范围内，避免组合爆炸。

#### used_routes 去重

每条路径维护一个 `used_routes` 集合（frozenset），避免在同一方案中重复乘坐同一条线路（无意义的绕路）。

### 4.3 时间复杂度

每层固定 2 条 SQL，最多 4 层（0~3 次换乘），总 SQL 数 ≤ 10 条。

Python 内存遍历的复杂度取决于 frontier 大小和每站的线路数，通过剪枝控制在可接受范围内。

实测 SF 数据（231 万 stop_times）：**0.5~2 秒**返回结果。

### 4.4 辅助函数

| 函数 | 职责 |
|------|------|
| `_get_stop_info(stop_id, region)` | 查站点名称，验证存在性 |
| `_get_routes_through_stops(stop_ids, region)` | 批量查站点经过的线路代表 trip |
| `_get_stops_for_trips(trip_ids, region)` | 批量查 trip 的完整站点序列 |
| `_get_name_from_segs(segments, stop_id)` | 从已有路段中查找站点名称 |
| `_deduplicate_plans(plans)` | 按线路+站点组合去重，保留最短时间 |
| `_finish(plans, strategy, ...)` | 去重、排序、截取前 5 条 |

## 5. 前端交互设计

### 5.1 站点选择

- 起点站：页面加载时预取前 500 个站点，el-select + filterable 本地过滤
- 终点站：显示全部站点，分两组展示
  - "直达可达站点"：选完起点后异步加载（通过 getStopRoutes + getRouteStops 获取起点站线路覆盖的站点）
  - "其他站点（需换乘）"：剩余站点
- 支持起终点交换（自动重新加载可达站点分组）

### 5.2 结果展示

- 方案卡片：换乘次数 badge + 预计时间
- 步骤时间线（el-timeline）：每段显示线路名（带颜色标签）、上下车站、经过站数、时间
- 终点标记

### 5.3 无结果处理

当找不到方案时（两站不在同一连通网络内）：
- 提示"两站可能属于不同运营机构的线路网络"
- 分别展示起点站和终点站经过的线路标签
- 高亮两站的共同线路（标注"可能方向不同"）

## 6. 已知限制

1. **最多 3 次换乘**：超过 3 次换乘的路径不会被搜索
2. **不考虑时间衔接**：当前只基于静态站点拓扑搜索，不考虑班次时间是否衔接（如第一段到达时间是否早于第二段发车时间）
3. **代表 trip 覆盖不完全**：同一 headsign 下如果存在站点序列不同的 trip 变体（短途/长途），只会取到其中一个
4. **跨运营机构不互通**：SF 地区包含 AC Transit、SF Muni 等多个运营机构，部分线路网络完全独立，无法通过换乘连通
5. **每站只保留 1 条最优路径**：剪枝策略可能遗漏某些换乘次数更多但实际更优的方案

---

## 7. 后续可优化方向

1. **时间衔接约束**：加入班次时间匹配，确保换乘方案在时间上可行
2. **shape_id 分组**：用 shape_id 代替 trip_headsign 做变体分组，更精确地区分不同站点序列
3. **预计算换乘图**：离线构建站点-线路邻接图，查询时直接在内存图上 BFS，无需实时 SQL
4. **步行换乘**：两个地理位置接近但不在同一站点的站，允许步行换乘（基于经纬度距离）
5. **多运营机构互通**：识别不同运营机构的相邻站点，建立虚拟换乘边
